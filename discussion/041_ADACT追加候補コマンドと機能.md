# 041: ADACT 追加候補コマンドと機能

## 背景

`discussion/037_UIAパターン対応要否.md` では、UIA Pattern ごとに ADACT で今後対応すべき領域を整理した。さらに `discussion/039_SampleApp_UIAパターン検証拡張_要件定義と設計.md` では、SampleApp を拡張して各 Pattern の観測性・操作性を見極める方針を設計した。

その後、実際に SampleApp を ADACT で操作し、`snapshot` / `inspect` / 既存サブコマンドでどこまで作業できるかを確認した結果、追加候補の優先順位について、より実務寄りの所感が得られた。

本メモは、その実操作結果を踏まえて、「今後 ADACT に何を足すと効果が大きいか」を discussion 文書として整理するものである。ここでの結論は確定仕様ではなく、**今回の SampleApp 検証結果から見た推奨**として扱う。

## 実際に SampleApp を ADACT で操作して得られた所感

今回の検証で特に大きかったのは、**操作そのものが全くできない場面よりも、状態の読み取りや判断材料が不足する場面の方が先にボトルネックになりやすい**、という点である。

- `click` / `select` / `fill` / `scroll-into-view` のような既存操作で、ある程度前進できる場面は多い。
- 一方で、「今どの項目が選択されているか」「このグリッドの何行何列に何があるか」「この要素がどの Pattern を持ち、その値が何か」を機械的に把握しにくい場面が残る。
- そのため、いきなり操作コマンドを増やすより、まず `inspect` を強くして **観測力を上げる** 方が、後続のコマンド設計にも効く。
- 特に DataGrid / List 系 / Tree 系では、既存操作で一見触れても、検証を安定させるには Pattern 由来の情報が必要だった。

この観点から見ると、最初に投資すべきなのは「より多く操作する手段」よりも「より正しく状況を理解する手段」である。

## 最優先で追加すべきもの

### `inspect` 拡張

#### 何をする機能か

`inspect` の出力に、現在より詳しい UIA Pattern 情報と Pattern 固有プロパティを含める。候補としては、少なくとも以下を読みやすく出せることが望ましい。

- Selection: 選択中要素、複数選択可否、選択必須か
- Grid / GridItem: 行数、列数、行 index、列 index、span
- Table / TableItem: 列ヘッダー、行ヘッダー
- Scroll: スクロール可否、方向、現在位置、表示割合
- RangeValue: 現在値、最小値、最大値、刻み、読み取り専用か
- Text: テキスト取得可否、選択範囲取得可否
- ExpandCollapse: 現在の展開状態

#### なぜ必要か

実操作の中では、未対応 Pattern に対して「専用コマンドがない」こと以上に、「何が起きているか分からない」ことが詰まりやすかった。`inspect` が十分に強ければ、次に追加すべき専用コマンドの要否も判断しやすくなる。

また、失敗時診断の改善にも効く。たとえば `select` がうまくいかない場合でも、Selection / ExpandCollapse / Scroll の情報が詳しく見えれば、対象側の性質を把握しやすい。

#### 現状の既存操作で代替できるか

代替しにくい。`snapshot` や操作結果の見た目だけでは、Pattern 固有の内部状態までは十分に読めないことが多い。

## 次に追加すべきサブコマンド / 機能

以下は、今回の SampleApp 検証結果から見て、`inspect` 拡張の次に検討価値が高い候補である。

### `get-selection`

#### 何をするコマンドか

ListBox、ComboBox、ListView、DataGrid、TreeView などに対して、現在選択されている要素を取得する。

#### なぜ必要か

選択系 UI では「選べる」ことだけでなく、「今どれが選ばれているか」を確認できることが重要である。特に複数選択や、見た目だけでは判断しにくい選択状態の検証で有効。

#### 現状の既存操作で代替できるか

部分的には `snapshot` や個別 `inspect` で推測できる場合もあるが、安定した取得手段としては不十分。実務上は専用コマンドが欲しい。

### `scroll`

#### 何をするコマンドか

スクロールコンテナに対して、水平・垂直方向へ量指定または割合指定でスクロールする。

#### なぜ必要か

`scroll-into-view` は対象 item が分かっているときには便利だが、コンテナ自体を少しずつ送る操作や、横スクロールを伴う表形式 UI では不足しやすい。

#### 現状の既存操作で代替できるか

マウスホイールや `scroll-into-view` で代替できる場面はあるが、対象依存・画面依存になりやすい。安定性の観点では専用化の価値がある。

### `grid-info` / `grid-get`

#### 何をするコマンドか

- `grid-info`: グリッドの行数・列数など構造情報を取得する。
- `grid-get`: 行・列指定でセルまたは該当要素を取得する。

#### なぜ必要か

DataGrid や表形式 ListView は業務 UI で頻出であり、行列ベースで扱えないと自動化・検証の難易度が高い。特に「何行目の何列目に何があるか」を確定的に扱えることが重要。

#### 現状の既存操作で代替できるか

既存の `snapshot` や要素探索だけでも近いことはできるが、構造把握とセル取得を安定して行うには厳しい。今回の検証結果からは、`get-selection` と並んで優先度が高い。

### `table-headers`

#### 何をするコマンドか

Table / TableItem に基づき、列ヘッダーや行ヘッダーを取得する。

#### なぜ必要か

グリッドの検証では、値だけでなく「その値がどの列に属するか」を確実に判断したい。列順の変化や UI 差異にも比較的強い検証ができる。

#### 現状の既存操作で代替できるか

ヘッダー文字列を別途探索して突き合わせることは可能だが、壊れやすい。Pattern ベースで取れるなら専用化した方がよい。

### `set-range`

#### 何をするコマンドか

Slider など RangeValuePattern を持つ要素に対して、値を直接設定する。

#### なぜ必要か

任意値に正確に合わせたい場合、クリックやキー入力だけでは再現性が低いことがある。レンジ系要素を値ベースで扱えると、テストが単純になる。

#### 現状の既存操作で代替できるか

キー入力やマウス操作で代替できるケースはあるが、刻み・初期位置・レイアウトに左右されやすい。専用コマンドがあると安定する。

### `get-text`

#### 何をするコマンドか

TextPattern を利用して、要素の全文や、必要に応じて選択範囲のテキストを取得する。

#### なぜ必要か

Label や単純 TextBox なら既存情報でも足りることがあるが、リッチテキストや文書ビューでは内容取得の確実性が落ちる。UI 上のテキストを検証するための明示手段として有用。

#### 現状の既存操作で代替できるか

Name / Value だけで読める場面もあるが、一般化しづらい。特に TextPattern が活きる対象では既存手段だけでは不十分。

### `find-item` / `realize`

#### 何をするコマンド / 機能か

- `find-item`: ItemContainerPattern を使って、仮想化リストやツリーから条件に合う item を探す。
- `realize`: VirtualizedItemPattern を使って、まだ実体化されていない item を操作可能な状態にする。

#### なぜ必要か

大量データや仮想化 UI では、画面に見えている範囲だけを `snapshot` しても十分でない。実業務アプリ寄りの UI に進むほど必要性が上がる。

#### 現状の既存操作で代替できるか

SampleApp 検証の範囲では必須場面は限定的だったが、既存操作だけでは本質的に代替しづらい。将来の必要性は高いが、優先順位は `inspect` / `get-selection` / `grid-get` より一段下と見るのが妥当。

### `expand` / `collapse`

#### 何をするコマンドか

TreeViewItem、ComboBox、MenuItem など ExpandCollapsePattern を持つ要素を明示的に展開・折りたたみする。

#### なぜ必要か

現在は `select` の副作用やクリックに頼る場面があるが、状態遷移を明示できる方がスクリプトの意図が分かりやすく、失敗時も切り分けやすい。

#### 現状の既存操作で代替できるか

ある程度は代替可能。ただし「選択したい」のか「展開したい」のかを分離できないため、専用コマンドがあるとより明確になる。

### `drag` / `drag-to`

#### 何をするコマンドか

要素から要素、または要素から座標へドラッグ＆ドロップを行う。

#### なぜ必要か

ドラッグ＆ドロップは特定領域では重要だが、今回の SampleApp 検証では最優先ではなかった。ただし既存の低レベルマウス操作だけでは、スクリプトが冗長かつ不安定になりやすい。

#### 現状の既存操作で代替できるか

`mouse-down` / `mouse-move` / `mouse-up` 相当で代替可能な場合はあるが、記述量と安定性の面で厳しい。必要性はあるが、観測系や表形式支援より後でよい。

### `wait-for` 条件拡張

#### 何をする機能か

既存の待機機能に、より実務向けの条件を追加する。候補としては、選択状態、展開状態、enabled / disabled、項目数変化、テキスト変化、進捗値変化などが考えられる。

#### なぜ必要か

実操作では「クリックできたか」より、「その結果として状態が変わるまで待つ」ことが重要である。特に動的 UI や非同期更新では、待機条件の弱さが不安定さにつながる。

#### 現状の既存操作で代替できるか

固定 sleep や単純な exists 判定では代替しきれない。既存機能の拡張として優先度は高いが、まずは `inspect` 側で観測可能な状態を増やすことが前提になりやすい。

## 逆に今は追加しなくてよいもの

以下は、少なくとも今回の SampleApp 検証結果から見る限り、優先度を上げなくてよい候補である。

### `StylesPattern` 操作系

- 何をするものか: 色、フォント、装飾などのスタイル情報を扱う。
- 今は追加しなくてよい理由: 自動化・機能テストより視覚検証寄りであり、ADACT の主目的からは一段遠い。
- 既存手段との関係: 本当に必要なら screenshot ベースや別系統の視覚比較の方が実用的な可能性が高い。

### `SpreadsheetPattern` 専用コマンド

- 何をするものか: スプレッドシート固有のセル式や注釈などを扱う。
- 今は追加しなくてよい理由: Excel 互換領域に寄っており、汎用 Windows UI 自動化の中核とは言いにくい。
- 既存手段との関係: まずは `grid-info` / `grid-get` / `table-headers` の汎用表形式支援を整える方が先。

### `TransformPattern2`

- 何をするものか: 主にズーム関連の操作を扱う。
- 今は追加しなくてよい理由: 今回の検証でも必要性は高くなかった。
- 既存手段との関係: ズームを自動化対象にする場面自体が限定的で、現時点では優先度が低い。

### `DockPattern`

- 何をするものか: UI 要素のドッキング位置変更を扱う。
- 今は追加しなくてよい理由: 業務 UI の通常操作や検証で頻出とは言いにくい。
- 既存手段との関係: 必要になるアプリがかなり限定的で、汎用コマンドとして先に追加する理由は弱い。

### `NotificationPattern`

- 何をするものか: ライブリージョン通知や UIA 通知イベントを扱う。
- 今は追加しなくてよい理由: これはイベント購読・監視寄りであり、現行の ADACT が主に対象としている「要素を見て操作する」流れとは少し軸が異なる。
- 既存手段との関係: まずは状態観測と通常操作の充実を優先した方が、利用者価値に直結しやすい。

## 推奨ロードマップ

### Phase 1: 観測力向上

最初の段階では、`inspect` 拡張を中心に、Pattern 情報の見え方を強化する。

- `inspect` の Pattern 固有情報を拡充する
- `get-selection` を追加する
- 可能なら `grid-info` を早期に入れ、グリッド構造を把握しやすくする

この段階の狙いは、専用操作を増やす前に「何が相手なのか」を正しく把握できる状態を作ることにある。

### Phase 2: 操作安定性向上

次の段階では、既存操作で代替はできるが不安定・冗長になりやすい領域を改善する。

- `scroll`
- `set-range`
- `expand` / `collapse`
- `wait-for` 条件拡張

この段階では、スクリプトの再現性と可読性を上げることが主眼になる。

### Phase 3: 既存操作で厳しい領域

最後に、既存操作では本質的に苦しい領域へ進む。

- `grid-get`
- `table-headers`
- `get-text`
- `find-item` / `realize`
- `drag` / `drag-to`

実際には `grid-get` は Phase 1 〜 2 相当の優先度で前倒ししてよく、ここでの Phase 3 はあくまで「汎用支援を超えて、より領域特化の操作へ入る段階」として見るのがよい。

## 結論

今回の SampleApp 検証結果から見ると、まず優先すべきなのは **`inspect` 拡張** である。そのうえで、次点として **`get-selection`** と **`grid-get`（必要に応じて `grid-info` を含む）** を優先するのがよい。

理由は、現在の不足が主に「操作不能」ではなく「状態把握不足」と「表形式 UI の扱いづらさ」に集中しているためである。まず観測力を高め、次に選択状態とグリッド操作を補強する流れが、今回の検証結果に最も整合的な推奨ロードマップと考えられる。
