# 038: README 要件定義

## 背景

OSS 公開を見据え、トップディレクトリの `README.md` を整備する。目的は、GitHub で初めて ADACT を見た人に「何のツールか」を短時間で伝え、最短で試せる状態に導き、公開リポジトリとしての信頼感を補強することにある。

現時点では配布導線が未整備のため、初期公開版 README はソースビルド前提で構成し、将来的に Release ダウンロードや配布手段が整った時点で導線を追加する。

また、過去の `discussion/` 文書にはライセンス未決として読める記述が残る可能性があるが、本件 README 方針では **MIT を採用する** ことを最新合意として扱う。README ではその前提を反映しつつ、必要に応じて「現時点の公開方針」であることが分かる表現にする。

---

## README の目的

README は詳細な設計書ではなく、公開入口として次を満たすことを目的とする。

- ADACT が **AI エージェント向けの Windows デスクトップ自動化 CLI** であると一読で伝わること
- 人間ユーザーにも、何ができるか・どう試すかの最短経路が分かること
- リポジトリ全体の詳細情報への案内板として機能すること
- OSS として最低限の安心材料（セットアップ、アーキテクチャ概要、貢献方法、ライセンス）を提示すること

---

## 想定読者

### 第一読者

- AI エージェント利用者
- AI coding agent / MCP 周辺ツールの利用者

この層には、ADACT が「ブラウザ自動化における Playwright 的な体験を Windows デスクトップ操作へ持ち込むツール」であることを強く訴求する。

### 第二読者

- Windows 自動化に関心のある開発者
- UIA / FlaUI / CLI ベースの自動操作に興味がある OSS 閲覧者

この層には、対象領域、構成、試し方、現在の成熟度が短く整理されていることが重要である。

---

## README に含めるべき内容

### 1. ツールの要約

- ADACT の正式名称
- 何をするツールか
- 何がユニークか（AI エージェント向け、Windows UI Automation、CLI 中心）
- 主対象が Windows デスクトップアプリであること

### 2. インストール

- 現時点では **ソースビルド前提** であることを明記する
- 必要な前提条件（Windows、.NET SDK、ビルド方法）を README レベルで簡潔に示す
- 詳細手順は必要に応じて `docs/` へ誘導する

### 3. クイックスタート

- 起動から最初の操作までの最短例を載せる
- 少数コマンドで「一覧取得 → attach → snapshot / 操作」の流れが分かること
- AI エージェント利用時のイメージが伝わること

### 4. アーキテクチャ概要

- `adact` CLI、daemon、UIA Engine の大まかな関係
- 詳細設計ではなく、利用者が混乱しないレベルの説明に留める
- より詳しい説明は `docs/architecture/overview.md` へ案内する

### 5. 貢献方法

- Issue / PR 歓迎の姿勢
- 開発時の基本コマンド（build / test）
- 詳細な開発情報は `docs/development/testing.md` や関連 docs へ誘導する

### 6. ライセンス

- README では **MIT License を現時点の採用方針として明記する**
- 過去 discussion に未決記述が残っていても、本要件定義では README 向け最新合意として MIT を採用した扱いに揃える

## README で強く打ち出すべきメッセージ

### AI エージェント向けであること

README 全体を通じて、ADACT は単なる UIA ラッパーではなく、**AI エージェントが使いやすい CLI / snapshot / ref モデルを備えた Windows 自動化ツール**であることを明確にする。

### すぐ試せること

公開初期は配布性よりも、リポジトリ clone 後に試せることを優先する。README は「後で詳しく読む」よりも「まず触る」を支援する構成にする。

### 公開リポジトリとしての信頼感

導入、利用開始、全体像、開発参加、ライセンスが不足なく揃っていることを示し、未整備な点は曖昧にせず明記する。

---

## README で避けたいこと

- 長大な内部設計説明に寄りすぎること
- `docs/` にある詳細仕様を README に重複展開すること
- 実装詳細やクラス責務の説明を前面に出すこと
- 将来未確定の配布方式を確定事項のように書くこと
- README 自体がセットアップ手順書・設計書・全コマンドリファレンス化すること

README は入口、`docs/` は詳細、`discussion/` は検討過程、という役割分担を維持する。

---

## 推奨章立て方針

公開初期の README は、概ね次の順序を推奨する。

1. タイトル
2. 1〜3 文の要約
3. 主な特徴 / できること
4. インストール（ソースビルド前提）
5. クイックスタート
6. アーキテクチャ概要
7. ドキュメント案内
8. 貢献方法
9. ライセンス

この順序により、閲覧者は「何か → なぜ面白いか → どう試すか → どう深掘るか」を自然に追える。

## 未整備事項と今後の扱い

### 配布導線

- 現時点では Release 配布、インストーラ、`.NET tool` 化などの導線は未整備
- そのため README では、**まずソースビルドで利用する** 前提を採る
- 将来的に配布導線が整ったら、README のインストール節を更新し、ソースビルド手順を補助的位置へ下げる

### 成熟度の見せ方

- 未整備事項は隠さず、初期公開段階の前提として率直に扱う
- 一方で、CLI・docs・テスト方針が存在することは信頼材料として提示する
- ライセンスのように過去文書との差分がある事項は、README 上で最新方針として自然に読める書き方を優先する

---

## Requirement フェーズ結論

- README は OSS 公開向けの **入口文書** として設計する
- 最重要メッセージは「ADACT は AI エージェント向けの Windows デスクトップ自動化 CLI」である
- 長すぎず、詳細設計に寄りすぎず、短時間で試せる導線を優先する
- 必須項目は **インストール、クイックスタート、アーキテクチャ概要、貢献方法、ライセンス(MIT)** とする
- MIT は過去文書の未決記述をそのまま踏襲したものではなく、**今回の README 方針における最新合意**として扱う
- 初期版は配布未整備を前提に **ソースビルド中心** で記述する
- 将来の Release 配布導線は README の拡張ポイントとして扱い、現段階では要件に含めるが本文では未整備として明記する

## Design フェーズ追記

Requirement フェーズの方針を前提に、README の見せ方と章構成について次を Design フェーズ合意として追加する。

### 冒頭メッセージ方針

- README 冒頭は **AI エージェント中心の一言説明** から始める
- 1〜3 文の汎用要約よりも先に、「誰のためのツールか」が即座に分かる導入を優先する
- 人間利用者を排除する意図ではなく、第一読者を AI エージェント利用者として明示するための設計とする

### 推奨構成

Design フェーズで合意した README の推奨構成は次の通り。

1. タイトル
2. AI エージェント中心の一言説明
3. 主な特徴 / できること
4. インストール
5. クイックスタート
6. アーキテクチャ概要
7. ドキュメント案内
8. Contributing
9. License

### 各章の役割

#### 1. タイトル

- リポジトリ名と正式名称を示す最小限の見出し

#### 2. AI エージェント中心の一言説明

- ADACT が **AI エージェント向けの Windows デスクトップ自動化 CLI** であることを最短で伝える
- `docs/README.md` や `AGENTS.md` にある現在のプロジェクト説明と整合する表現へ寄せる

#### 3. 主な特徴 / できること

- snapshot / ref モデル、CLI 中心、Windows UI Automation 対象といった差別化要素を短く整理する
- 全コマンド羅列や詳細仕様説明には入らず、詳細は `docs/spec/cli.md` へ逃がす

#### 4. インストール

- 公開初期はソースビルド前提であることを簡潔に示す
- 必須前提と最小 build 導線のみを載せ、詳しい補足は docs へ誘導する

#### 5. クイックスタート

- 基本操作フローとして **daemon 起動（`adact serve pipe` / `adact serve http`）→ `list-apps` → `attach` → `snapshot` → 操作** を追える構成にする
- ここで README の入口性を優先し、最短で「動く」体験を与える
- あわせて `install --skills` 系の導線も **数行だけ** 含め、AI coding client 連携の入口があることを示す
- ただし `install --skills` の詳細仕様や client ごとの差分説明は README に展開しすぎず、必要なら `docs/spec/cli.md` や関連 discussion を参照させる

#### 6. アーキテクチャ概要

- `adact` CLI、daemon、Engine、Windows app の関係を把握できる最小説明に留める
- 内部クラス責務や詳細フローは `docs/architecture/overview.md` 以降へ委譲する

#### 7. ドキュメント案内

- README を読んだ後の次の導線として、architecture / spec / development docs へのリンク集を置く
- README 本文を肥大化させず、詳細情報の集約先を `docs/` に固定する

#### 8. Contributing

- **軽く保つ** ことを明示方針とする
- PR 歓迎の姿勢と、最低限の build / test コマンド案内に留める
- 開発規約、テスト層の詳細、設計前提は docs や `AGENTS.md` 側へ逃がす

#### 9. License

- License は README の末尾に置き、公開リポジトリとしての基本情報を締める役割にする
- 内容上の扱いは Requirement フェーズで合意した MIT 方針を踏襲する

### README の深さに関する判断

- README はあくまで **入口文書** に徹し、内部設計詳細は `docs/` 側へ逃がす
- 特に architecture、CLI コマンド仕様、開発手順の詳細を README 本体へ持ち込みすぎない
- Design フェーズでは、README 本文案や文言の完成形よりも、章の責務分担と情報量の上限を先に固定する

### Design フェーズ結論

- README 冒頭は AI エージェント中心の一言説明を採用する
- 推奨構成は **タイトル → 一言説明 → 特徴 → インストール → クイックスタート → アーキテクチャ概要 → ドキュメント案内 → Contributing → License** とする
- クイックスタートには基本操作フローに加えて、`install --skills` 系の導線を短く含める
- Contributing は軽量に保ち、PR 歓迎と最小 build / test 案内に留める
- README は入口文書、詳細仕様と内部設計は `docs/` へ委譲する
