# 043 コマンド改善案

## 1. close / kill — graceful shutdown の導入

### 現状

- **close**: UIA `WindowPattern.Close()` → `PostMessage(WM_CLOSE)` で**ウィンドウを閉じる**。アプリ側で拒否可能。成功後 session は自動 detach。プロセスは生き続ける。
- **kill**: `Process.Kill(entireProcessTree: true)` で**プロセスを即時強制終了**。猶予ゼロ。成功後 session は自動 detach。

### 課題

kill が graceful shutdown の猶予を与えないため、アプリがファイル保存などの後処理をする余地がない。

### Windows の技術的背景

- Windows に Unix のシグナル (SIGTERM, SIGKILL) は存在しない。
- ウィンドウ単位の強制終了は Windows API の制約で不可（`DestroyWindow` は同一スレッドのウィンドウのみ操作可能）。
- graceful shutdown の実現手段:
  1. 対象プロセスの全トップレベルウィンドウを列挙 (`EnumWindows`)
  2. 各ウィンドウに `PostMessage(WM_CLOSE)` を送る
  3. タイムアウト付きでプロセス終了を待つ
  4. タイムアウトしても生きていれば `Process.Kill()` にフォールバック

### 主な選択肢

| 案 | 内容 | 後方互換 |
|---|---|---|
| C: `kill --graceful` | デフォルトは即死維持。`--graceful` 指定時は WM_CLOSE → timeout → force kill。`--timeout` でタイムアウト値も指定可能。 | ✅ 維持 |
| D: `terminate` 新設 | `kill` = 即死（現状維持）、`terminate` = graceful → fallback kill。SIGKILL / SIGTERM の関係を表現。 | ✅ 維持 |
| A: `kill` 自体を graceful-first | 常に WM_CLOSE → timeout → force kill。シンプルだが既存の即死期待を壊す。 | ❌ 破壊的 |

## 2. select — 複数要素選択への対応

### 現状

- `--name` / `--index` / `--item-ref` のうち**ちょうど1つだけ**指定必須（CLI / MCP / Engine の全レイヤーでバリデーション済み）。
- 複数要素の同時選択は不可。

### 課題

ListBox など複数選択可能なコントロール (SelectionMode=Multiple/Extended) で複数アイテムを選択できない。

### UIA の技術的背景

- `SelectionPattern` (コンテナ側): `CanSelectMultiple` で複数選択対応の有無を判定可能。
- `SelectionItemPattern` (個別アイテム側):
  - `Select()` — 現在の選択をクリアして自分だけを選択
  - `AddToSelection()` — 現在の選択に自分を追加
  - `RemoveFromSelection()` — 現在の選択から自分を除外
- ADACT は現状 `Select()` のみ使用。

### 主な選択肢

| 案 | 内容 | 備考 |
|---|---|---|
| A: 複数回指定 + モード | `--name "Item1" --name "Item2"` で複数指定。`--add` / `--remove` で追加/除外モードを選択。 | CLI として自然。System.CommandLine の `AllowMultipleArgumentsPerToken` で実装可能。 |
| B: セパレータ区切り | `--name "Item1,Item2"` で一括指定。`--mode add` で動作切替。 | コマンドラインが短い。アイテム名のカンマ問題あり。 |
| C: サブコマンド化 | `select set` / `select add` / `select remove` に分割。 | 操作が明確だが階層が深くなる。後方互換性喪失。 |
| D: `--name` のみ複数化（置換専用） | まずは `Select()` による置換だけ複数対応。`--add` / `--remove` は後日。 | シンプル優先。 |

## 3. resize — 片方の寸法だけ変更可能に

### 現状

- `--width` と `--height` が**両方必須**（CLI / MCP / Engine の全レイヤー）。
- どちらか片方だけの指定はパースエラー。

### 課題

「幅だけ変えたい」「高さだけ変えたい」という操作ができない。

### UIA の技術的背景

- `TransformPattern.Resize(width, height)` は両方の値が必須（片方だけのオーバーロードは存在しない）。
- しかし現在のウィンドウサイズ (`BoundingRectangle` など) を読み、未指定の寸法を補完すれば機能的には実現可能。
- つまり UIA API の制約ではなく、ADACT が未対応なだけ。

### 実装方針

**推奨: 現在サイズを読んで補完する方式**

```csharp
// 現在のウィンドウサイズを取得
var current = session.GetWindowBounds();  // → {Width, Height}
// 指定のなかった方は現在値を維持
args["width"]  = w ?? current.Width;
args["height"] = h ?? current.Height;
// Resize を実行
transform.Resize(width, height);
```

- CLI: `--width` と `--height` を両方とも省略可能にする（少なくとも1つは必須のバリデーションを追加）。
- Engine: 現在のサイズを取得する機構が必要。`_window.Properties.BoundingRectangle` が使える。

## 4. mouse-wheel — 両方未指定時のエラーチェック

### 現状

- `--delta-x` / `--delta-y` は両方とも省略可能（デフォルト 0）。
- 両方 0 の場合、MCP ツール層で `if (deltaY != 0)` / `if (deltaX != 0)` のガードにより何もせず、成功を返す。
- つまり `adact mouse-wheel` (引数なし) が exit 0 で素通りする。

### 課題

ユーザーの指定ミス（例: `--delta-x` を `--deltax` と typo）が気づかれずに素通りする。

### 実装方針

**推奨: CLI 層で両方 0 の場合にエラーにする**

```csharp
if (dx == 0 && dy == 0)
    return Task.FromResult(OperationOptions.ReportUserError(
        "Provide at least one of --delta-x or --delta-y with a non-zero value."));
```

または UI の作法として Warning を出すだけも考えられるが、ミスを確実に検知するにはエラーのほうが親切。

### 適用場所

CLI 層 (`MouseWheelCommand.cs`) で行う。MCP ツール層は 0 を許容したままでも問題ない（プログラムから呼ばれる場合に柔軟性を保てる）。
