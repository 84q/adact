# 008 要件再整理 — Phase 5 以降の方針

Phase 4 完了後、Phase 5 着手前にユーザと再確認した結果、ADACT の最終ビジョンと既存ドキュメント (001/003) との間に乖離があることが判明した。本書は Phase 5 以降の方針を確定するための要件再整理。

参考: [Playwright Agent CLI](https://playwright.dev/agent-cli/introduction) (`@playwright/cli`) — Coding AI 向けの CLI ツール。daemon アーキテクチャ、Ref-based、Sessions、Token-efficient、Skill-based。ADACT はこのモデルに準拠する。

## 1. 背景: 既存ドキュメントとの乖離

### 1.1 ADACT 本来の姿 (001 で確定済の事項)

- 名称: ADACT = AI-driven Desktop Application **Cli Tools** ([001 L3](001_要件定義.md))
- 操作: Click / Fill / Type / Press / Hover / Select を「実行する」 ([001 L18, L46](001_要件定義.md))
- Phase 2 完了条件: 「**ADACT CLI 単体で** Snapshot / Click / Fill が動く」 ([001 L68](001_要件定義.md))

### 1.2 これまでの実装計画 (Phase 3〜5) の偏り

[001 L91](001_要件定義.md) と [003](003_実装計画.md) では「Phase 2 CLI のサブコマンドは list/snapshot のみ。click/fill は Engine API として実装し L4 スモークで検証」とされ、その後の Phase 3〜5 は **MCP 中心**で計画されていた:

- Phase 3: stdio MCP server (`adact local`)
- Phase 4: HTTP MCP server (`adact serve`)
- Phase 5: stdio→HTTP プロキシ (`adact` 既定モード)

この計画では「Coding AI が MCP プロトコルを直接話す」前提になっており、CLI として人間や AI が叩く要件 (001 L18/L46/L68) が抜け落ちていた。

### 1.3 新ビジョン (再確認結果)

> **AI は ADACT CLI を操作する。ADACT CLI はローカル、あるいは遠隔の MCP を通してデスクトップアプリを操作する。Coding AI は基本的には、直接 MCP にアクセスしない。(Playwright CLI と同様)**

```
[Coding AI / Human]
       │ shell exec
       ▼
[adact <subcommand>]              ← Phase 5: CLI クライアント
       │ MCP/HTTP
       ▼
[adact serve]  (常駐 daemon)       ← Phase 4 で実装済
       │ in-process UIA
       ▼
[Windows]
```

Phase 4 までの成果物 (`adact serve`, `Adact.Mcp.Common`, `UiaEngine`, `WindowSession`) はすべて活きる。**`adact serve` を daemon として再利用し、CLI を MCP HTTP クライアントとして新規実装**するのが Phase 5。

## 2. 確定要件

### 2.1 主インターフェース

- **`adact <subcommand> [args...]` の CLI を主インターフェースとする**
- Coding AI も人間も同じ CLI を叩く (Playwright Agent CLI モデル)
- Coding AI は基本的に MCP プロトコルを直接話さない

### 2.2 アーキテクチャ

| コンポーネント | 役割 |
| --- | --- |
| `adact <sub>` (CLI) | MCP/HTTP クライアント。短命プロセス |
| `adact serve` (daemon) | HTTP MCP server。常駐、Session/Ref ID をメモリ内に保持 |
| `adact local` (stdio MCP server) | 当面残す (互換性目的)。最終的に削除候補 |
| `Adact.Mcp.Common` | daemon が公開する MCP ツール定義 |
| `UiaEngine` / `WindowSession` | in-process UIA 操作の実体 |

### 2.3 セッション・Ref ID の永続化

- Ref ID (`s<sid>g<gen>e<eid>`) と Session は **daemon プロセス内のメモリで保持**する
- daemon が常駐している限り、CLI 短命プロセスをまたいで Ref ID は有効
- ディスク永続化は不要 (daemon 終了時に状態リセットでよい)

### 2.4 接続先指定 (要件レベル)

- ローカル daemon (`http://127.0.0.1:<port>`) は **既定値として設定不要**で動くこと
- リモート daemon への接続も **指定可能であること**
- 接続先指定の **複数手段** をサポートする (CLI option / 環境変数 / 設定ファイル等)
- 認証情報 (将来) は安全に保管する仕組みを持つこと

具体的な指定方式・優先順位・ファイル形式は **Phase 5 設計フェーズ** で決定する。

### 2.5 出力形式

- CLI 出力は **token-efficient** であること (Playwright Agent CLI 同様)
- snapshot は本体をファイルに保存し、CLI 標準出力にはファイルパス + 概要だけを返す方針 (snapshot は MCP ツールと CLI で形態が異なる例)
- MCP ツールと CLI サブコマンドは **基本 1:1 対応** だが、必須ではない

### 2.6 Skill 機構

- Coding AI 向け Skill (capability 提供) を採用する (差別化要素)
- 詳細は Phase 6 で設計・実装

## 3. Phase 構成 (再構成)

| Phase | 状態 | スコープ |
| --- | --- | --- |
| Phase 1〜3 | 完了 | (既存通り) |
| Phase 4 | 完了 | HTTP MCP server (`adact serve`) — daemon の役割を担う |
| **Phase 5** | 新規 | **CLI 基本実装**。Phase 3 MCP 5 種に対応する CLI: `list-apps` / `attach` / `snapshot` / `click` / `fill`。`adact serve` daemon に MCP HTTP クライアントとして接続。**接続先指定の方式設計を含む** |
| **Phase 6** | 新規 | **Skill 機構**。最初は Phase 5 の 5 サブコマンドのみカバー。以降随時拡張 |
| **Phase 7** | 新規 (旧 Phase 6 再構成) | **安定化** (CLI 拡張以外)。モーダルダイアログ検出/追随、画面ロック時エラー、構造化ログ基盤、Snapshot サイズチューニング、`AttachQuery.Hwnd` 拡張、失敗時詳細ログ等。**必要なサブコマンドは Phase 8 を待たず随時実装可** |
| **Phase 8** | 新規 | **サブコマンド拡張 + コマンド体系整理**。`close` / `launch` / `wait-for` / `screenshot` / `hover` / `press` / `type` / `keydown/up` / `mousemove/down/up` 等。Playwright Agent CLI のコマンド体系を参照しつつ ADACT のコマンド一覧を整理 |
| **Phase 9+ (候補)** | 未確定 | Dashboard、OCR、安定セレクタ生成、Codegen、state 永続化等。採否は Phase 8 完了時に再判断 |

### 3.1 旧 Phase 5 (stdio→HTTP proxy) の扱い

新ビジョンでは Coding AI が stdio MCP を直接話さないため、**proxy は不要化**。スコープから削除する。

### 3.2 stdio MCP (`adact local`) の今後

- Phase 5 以降も当面残す (Claude Desktop 等の他 MCP クライアントとの互換性)
- 利用実態が乏しいことが確認できた段階で削除を判断

## 5. Phase 5 設計フェーズへの申し送り

Phase 5 設計フェーズで決定すべき事項:

- 接続先指定方式の詳細
  - CLI option / 環境変数 / 設定ファイル の組み合わせと優先順位
  - 設定ファイル形式 (TOML/JSON/YAML)
  - リポジトリ共有設定 (`.adact`) と個人設定の分離
  - 検索ルール (カレントから上位ディレクトリへの探索等)
- daemon 自動 spawn の有無 (CLI 初回呼び出し時に `adact serve` を裏で起動するか)
- in-process CLI モード (server 不要モード) の有無
- 認証・通信暗号化の初期スコープ (Phase 4 で localhost 限定としたため、Phase 5 で再判断)
- CLI 出力形式の詳細 (Page state ヘッダ、snapshot ファイル保存ルール、`--json` フラグ等)
- サブコマンド命名規則と引数体系
- エラー出力規約 (exit code、stderr 形式)
- daemon 接続失敗時のメッセージ・対処指示
- Ref ID の有効性チェック (古い Ref ID を使った場合の挙動)
- daemon 再起動時の Session 喪失をユーザにどう伝えるか

## 6. Phase 6 以降の申し送り (Phase 5 以降の設計時に検討)

- Skill 機構の設計 (Phase 6): Skill ファイル形式、配置、配布、`adact install --skills` 相当の有無
- Phase 7 安定化項目の優先順位付け
- Phase 8 でのコマンド体系整理 (Playwright Agent CLI からの取り込み範囲)
- Phase 9+ 候補機能 (Dashboard / OCR / Codegen / state 永続化) の採否再判断
