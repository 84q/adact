# 011 Element Ref 安定化 (Phase 5 ポストタスク)

> 前提: [001_要件定義.md](001_要件定義.md) §9 / [009_Phase5設計.md](009_Phase5設計.md) §7 / [010_Phase5_完了.md](010_Phase5_完了.md)
> 目的: 操作後 snapshot 取得時に Element Ref ID が古くならない仕組みを導入し、AI のコンテキスト窓消費を削減する。

## 1. 背景・課題

Phase 5 完了後の手動スモークで判明した課題。

- 現状: `click` / `fill` 成功時に snapshot 自動再取得 → generation +1 → 既存 Element Ref が全て STALE 化
- 影響: 同一画面で連続操作する用途 (AI による電卓連打、フォーム入力連続実行 等) で、毎回 JSON 再読込が必要となり Coding AI のコンテキスト窓消費が大きい
- 自動 snapshot 自体は UI 状態把握のため維持したい → ref 側を世代非依存にする必要がある

## 2. 関連調査

### 2.1 Playwright MCP の挙動

- アクション系ツール (`click` 等) はレスポンスに snapshot を自動添付する
- ref は連番だが **同一要素では世代をまたいで再利用** される
- 仕組み: DOM 要素プロパティ `_ariaRef` に ref をキャッシュ、role+name 不変なら同じ ref を返す
- 補助策として差分描画 (`[unchanged]`)、`target` による部分 snapshot、`--snapshot-mode=none` などコンテキスト削減オプションを併用

### 2.2 UIA RuntimeId の特性

- 仕様: opaque comparison key、デスクトップ内一意、再利用される可能性あり (Microsoft 公式)
- 同一プロセス稼働中・同一要素では事実上安定
- 限界: virtualized ListView での要素再生成、トップレベルウィンドウ等で NULL、MSAA proxy 経由で空配列

### 2.3 spike (flaui-b) 実機計測

| App | 取得率 | AutomationId 重複 |
|---|---|---|
| adact (VSCode) | 100% (4 levels) | 0 |
| explorer | 100% (4 levels) | 1 ケース (Edit/TextBox) |
| notepad++ | 100% (4 levels) | 1 ケース (Text/ContentTextBlock) |
| 電卓 | 100% (4 levels) | 0 |

→ 主要対象アプリで RuntimeId は 100% 取得。AutomationId 重複は実在するため一意キーとしては不適。

## 3. 要件

- AI が同一画面で連続操作する際、ref が世代をまたいで安定すること
- 操作後の自動 snapshot は維持 (UI 状態把握の即時性は失わない)
- generation 概念は廃止し、Ref ID を `s<sid>e<eid>` に簡素化
- 万一 ref が要素消失で無効化された場合は `STALE_REF` (既存) を返す

## 4. 設計

### 4.1 Element Ref ID フォーマット変更

`s<sid>g<gen>e<eid>` → `s<sid>e<eid>`

- 例: `s1e7` (session 1 の 7 番目要素)
- フォーマット regex: `^s\d+e\d+$`
- 後方互換: なし (フェーズ同期、即切り替え)

### 4.2 ref 採番ロジック

Playwright `_ariaRef` 等価の Map ベース実装。

- WindowSession 内に `Dictionary<string StableKey, int eid>` を保持
- snapshot 取得時に各要素の `StableKey` を計算
- 既存キーがあれば既存 eid を再利用、無ければ単調増加カウンタで採番
- カウンタは引退要素分も詰めない (Playwright と同じ挙動)

### 4.3 StableKey 算出

優先度順。

1. **RuntimeId が取得可・非空** → `"rid:" + string.Join("-", rid)`
2. それ以外 → 最小実装として `"unstable:" + 要素出現順 index`
   - ※ 完全な合成キー (親パス + AutomationId + ChildIndex 等) は将来課題 ([§7](#7-将来課題-phase-7))
   - 出現順 fallback でも「同 snapshot 内では一意」は守れる
   - ただし「次の snapshot との対応付け」は弱いため、要素状態が変わると新 ref になる可能性あり (Phase 5 ポストの許容範囲)

### 4.4 STALE_REF の発火条件

- 要素が UIA から取得不可 (`ElementNotAvailableException`)
- ref に対応する StableKey が現 snapshot に存在しない
- (注: generation 廃止により「世代不一致」は発火条件から外れる)

### 4.5 generation 番号の扱い

- MCP ツールレスポンス / CLI 出力から `generation` フィールドを除去
- snapshot ファイル名から `gen-N` を除去: `.adact/session-1-20260428T180000000.json`
- 「snapshot revision (何回目の snapshot か)」として残す案もあるが、フォーマット混乱を避けるため **完全廃止**

### 4.6 出力フォーマット影響

設計 [009](009_Phase5設計.md) §5.2 への差分。

- attach 出力: `generation N` 行を削除
- click / fill / snapshot 出力: `generation N` 行を削除
