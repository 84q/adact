# 018 対話セッション判定 — `adact serve` / `adact local` 起動時ガード

> 関連: [009 Phase5 設計 §6](009_Phase5設計.md) (エラーコード規約) / [015 Phase7 要件定義](015_Phase7要件定義.md) / [017 Phase7 完了](017_Phase7_完了.md)
> 作成日: 2026-04-29 (JST)

## 1. 背景

SSH 経由の PowerShell から `adact serve` を起動したところ、`adact list-apps` および MCP `windows_list_apps` が 0 件しか返さなかった。原因は ADACT デーモン自身が **対話デスクトップを持たない Windows セッション (例: SessionId 0 / `Service-0x0-...$` Window Station)** で動作していたことで、UIA は同一セッション内の top-level window しか見えないため空配列となっていた。

実測例 (本ワークスペース):

| プロセス | SessionId |
| --- | --- |
| SSH 上の powershell | 0 |
| explorer.exe / CalculatorApp | 1 |

このとき `list-apps` の空応答は「該当ウィンドウなし」と区別できず、利用者は ADACT のバグや電卓未起動を疑うことになる。事故の本質は **デーモンの起動セッションを起動時に検証していない** 点にある。

## 2. 目的

ADACT デーモン (HTTP `serve` / stdio `local`) の **起動時に**「現在のプロセスから GUI ウィンドウへ UIA アタッチできるセッションか」を判定し、不可能な場合は **明確なエラーで起動を拒否** する。これにより:

- 利用者は「セッションが違う」事故を起動失敗として即時に検知できる
- `list-apps` 等の後段ツールは「daemon が応答するなら対話セッション内」という前提を満たすため、追加の診断分岐が不要になる

## 3. スコープ

- 対象: `adact serve` (HTTP) および `adact local` (stdio MCP)。両者とも UIA を使用するため同じ判定を適用する
- 非対象:
  - すでに起動済の daemon に対する CLI クライアント側の判定 (CLI は HTTP/stdio 越しにしかセッションを観測できないため、責務は daemon 側に置く)
  - RDP / コンソール等、対話セッションの種類による振り分け (§4 の通り対話セッション内であれば UIA 機能は同等)
  - daemon 起動後にユーザーがログオフ / セッション切替した場合の動的検知 (起動時のみ判定する)

## 4. 要件

### 4.1 機能要件

- F1. daemon プロセスは、UIA の利用準備に先立って自己セッションを判定する
- F2. **対話デスクトップ非所属** と判定された場合は MCP listener (HTTP / stdio) の起動前にエラー終了する
  - 終了コード: 既存の `1` (CommandFailed) ではなく、専用の意味を担う **`4`** を新設する。`1`/`2`/`3` は既に「daemon が応答した実行失敗」「ユーザー入力エラー」「接続失敗」に割り当てられており (009 §6.1)、本ケースは「daemon が起動できなかった環境エラー」として独立させるため
- F3. エラー出力は stderr に既存の `error / message / hint` 形式 (009 §6.2) で出す
  - 新規エラーコード: **`NO_INTERACTIVE_SESSION`**
  - `message` には観測した SessionId と Window Station 名を含める (例: `daemon is not in an interactive desktop session (SessionId=0, WindowStation="Service-0x0-3e7$")`)
  - `hint` には「対象 GUI が動いている対話ログオンセッション側で起動してください」を案内する
- F4. 判定は **WindowStation が `WinSta0` であること** を必要十分条件とする (詳細 §5.1)。SessionId 0 / 非 `WinSta0` のいずれも `NO_INTERACTIVE_SESSION` で弾く
- F5. 上記の判定結果は daemon の通常ログ (stderr 既存ログ経路) に1行残す。成功時は `info` 相当で観測値 (SessionId / WindowStation) を記録、失敗時は §F3 と整合する内容

### 4.2 非機能要件

- N1. 判定は数 ms 以内で完了する純粋な API 呼び出しのみで構成する (UIA 初期化前に行う)
- N2. 追加依存は P/Invoke のみ。新規 NuGet 参照を増やさない
- N3. 判定ロジックは **純関数化** (`SessionId` と `WindowStation` 名を入力に判定結果を返す形) し、Unit テスト (L1) でカバーする
- N4. 既存の `--server` 接続経路や `daemon-stop` の動作には影響を与えない (起動済み daemon の振る舞いは現状維持)

## 5. 設計

### 5.1 判定ロジック

入力:

- `sessionId`: `Process.GetCurrentProcess().SessionId`
- `windowStationName`: `GetProcessWindowStation()` の戻りに対し `GetUserObjectInformation(UOI_NAME)` で取得した文字列

判定:

| 条件 | 結果 |
| --- | --- |
| `sessionId == 0` | `NO_INTERACTIVE_SESSION` |
| `windowStationName != "WinSta0"` (大文字小文字無視) | `NO_INTERACTIVE_SESSION` |
| 上記いずれにも該当しない | OK |

補足:

- RDP セッションは独立した `WinSta0\Default` を持ち、同一セッション内のプロセスから UIA で全ウィンドウを操作できる。よって `WTSGetActiveConsoleSessionId` との一致は判定条件としない
- `sessionId == 0` の場合は理論上 `WindowStation` も `WinSta0` にならないが、観測値をエラーメッセージに含めたいため両者を独立に取得する
- 判定は P/Invoke 失敗時 (例: `GetUserObjectInformation` が `ERROR_INVALID_HANDLE` 等) も `NO_INTERACTIVE_SESSION` 扱いとする (デスクトップに到達できない状況であるため)

### 5.2 配置

| 要素 | 配置 | 備考 |
| --- | --- | --- |
| P/Invoke 宣言 | `Adact.Engine/NativeMethods.cs` | 既存 NativeMethods に `GetProcessWindowStation` / `GetUserObjectInformation` を追記 |
| 判定純関数 | `Adact.Engine/InteractiveSessionGuard.cs` (新規) | `static InteractiveSessionGuard.Check(sessionId, windowStationName)` のように、観測値を引数に取り `(bool ok, string? code, string? message)` を返す形にする |
| 観測値取得 | `InteractiveSessionGuard.Probe()` (新規) | `Process.GetCurrentProcess().SessionId` と `GetUserObjectInformation` を呼び出し、`Check` を内部で呼ぶ薄いラッパ |
| 呼び出し点 (HTTP) | `Adact.Cli.Server/HttpHost.RunAsync` の冒頭 | `BuildApplication` の前に判定。失敗時は stderr 出力後 exit 4 で `Environment.Exit` ないし `return` 経由で `Program.Main` に戻す |
| 呼び出し点 (stdio) | `Adact.Mcp.Stdio/McpStdioServer` の起動経路 | listener 開始前に同 API を呼ぶ |

### 5.3 終了コード / エラー出力

`Adact.Cli/Output/ExitCodes.cs` に以下を追加 (既存の `Success=0 / CommandFailed=1 / UserError=2 / ConnectionFailed=3` に続けて):

| 名前 | 値 | 用途 |
| --- | --- | --- |
| `EnvironmentNotSupported` | 4 | daemon を起動できない環境を検出した場合の終了コード |

`Adact.Mcp.Common/ToolErrors.cs` (または CLI 側の `ErrorCodes.cs`) に新規コードを追加:

| 名前 | 値 (string) |
| --- | --- |
| `NoInteractiveSession` | `NO_INTERACTIVE_SESSION` |

stderr 出力例:

```
error NO_INTERACTIVE_SESSION
message daemon is not in an interactive desktop session (SessionId=0, WindowStation="Service-0x0-3e7$")
hint launch 'adact serve' from the interactive logon session that owns the target GUI windows
```

`adact local` でも同形式で出力する (stdio MCP のため stdout は MCP 用に確保しなければならない点は既存規約通り)。

### 5.4 ドキュメント反映

実装フェーズで以下を更新する:

- `docs/api/` (もし serve / local 起動時のエラーを記載している箇所があれば): `NO_INTERACTIVE_SESSION` の追加
- `docs/development/`: トラブルシュート章に「SSH やサービス経由で起動した場合に NO_INTERACTIVE_SESSION で失敗する。対話セッション側で起動すること」を追記
- `discussion/009_Phase5設計.md` §6.3 のエラーコード一覧へのクロスリファレンス (本書を参照)

## 6. テスト方針

`testing-strategy` skill の階層に沿って:

- **L1 Unit (`Adact.Engine.Tests`)**: `InteractiveSessionGuard.Check` の純関数テスト
  - `(0, "WinSta0")` → fail
  - `(1, "Service-0x0-3e7$")` → fail
  - `(1, "winsta0")` (case-insensitive) → ok
  - `(2, "WinSta0")` → ok (RDP 等を許可)
- **L4 Smoke (`Adact.Mcp.Http.Tests`)**: 既存の `AdactHttpServerFixture` で daemon が起動できる (= テスト実行ホストが対話セッションである) ことを暗黙にカバー。新規 smoke は追加しない
- **L4 Smoke (Cli)**: `Process` を `CreateProcessAsUser` で session 0 に投げ込むテストは複雑かつ環境依存のため見送り。Unit でロジックを保証し、実セッションでの fail-fast は手動スモークで確認 (§7)
- **L5 E2E**: 既存の Calculator E2E は対話セッションでのみ動作するため、本変更で挙動は変わらない

## 7. 手動スモーク

実装後に開発者が一度確認する手順:

1. **正常系 (対話セッション)**
   ```powershell
   adact serve
   # 標準ログに 'interactive session ok (SessionId=1, WindowStation=WinSta0)' 相当の info が出る
   ```
2. **異常系 (SSH / 非対話)**
   ```powershell
   # SSH 接続した先で
   adact serve
   # exit code 4、stderr に NO_INTERACTIVE_SESSION
   ```
3. **stdio 経路**
   ```powershell
   # session 0 で
   adact local
   # 同様に exit 4 / NO_INTERACTIVE_SESSION
   ```

## 8. 既知の制約 / 後続課題

- C1. daemon 起動後にユーザーがログオフした場合の自動シャットダウンは行わない (UIA 呼び出しが個別に失敗するに任せる)。必要であれば後続フェーズで `WTSRegisterSessionNotification` 等の検討
- C2. 同じ判定を将来的に Windows サービスとして起動する形態 (Phase 9 以降の自動 spawn 構想) で再検討する必要あり。サービス起動時は `CreateProcessAsUser` 経由で対話セッション側の helper を起こす設計になるため、本判定はその helper 側で動くことを前提とする
- C3. テストカバレッジは Unit に閉じる。session 0 への注入を伴う統合テストは将来必要になった段階で検討
