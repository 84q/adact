# ADACT 要件定義

対象: ADACT (AI-driven Desktop Application Cli Tools)

***

## 1. 背景

* AI エージェント（Claude Code / Cursor / GitHub Copilot 等）がブラウザを操作するための基盤として、Playwright MCP (Model Context Protocol) が標準化されつつある。
* 一方で **Windows デスクトップアプリ** に対する同等の仕組みは、断片的な先行プロジェクト（FlaUI-MCP, Windows-MCP 等）こそ存在するものの、運用面・アーキテクチャ面で未成熟。
* Windows デスクトップアプリを AI に操作・テストさせられる、**運用しやすく汎用的な** ツールが欲しい。

* Playwright MCP の設計思想（Snapshot + Ref ID による構造的操作）を Windows デスクトップの世界に持ち込む。
* [Playwright Agent CLI](https://playwright.dev/agent-cli/introduction) と同様、**ADACT CLI を主インターフェース**として提供し、Coding AI (Claude Code / Copilot 等) も人間も shell から同じ CLI を叩いて以下を行える環境を提供する：
  * Windows アプリの UI 構造を「読む」（Snapshot）
  * 要素単位の操作を「実行する」（Click / Fill / Press 等）
  * 上記をテストコードとして「残す」（将来機能）
* MCP server (`adact serve`) は ADACT CLI のバックエンド (daemon) として動作し、別の MCP クライアント (Claude Desktop 等) からも直接利用できる。

> 詳細な背景・経緯は [008_要件再整理.md](008_要件再整理.md) を参照。

## 3. ターゲットユーザー / ユースケース

* 開発者・QA が、AI エージェントを使って Windows アプリの操作・E2E テストを書く / 動かす。
* 手元のローカルマシンで AI エージェントを動かしつつ、**テスト対象アプリは別のマシン**（CI 用 / QA 用 PC 等）で動作させたいケースを含む。

## 4. スコープ

### 4.1 対象

* **UIA (UI Automation) で情報取得・操作が可能な Windows デスクトップアプリ**。
* 具体的には WPF / WinForms / UWP / Win32（UIA 対応済み）。

### 4.2 非対象（初期）

* UIA が効かない or 極端に貧弱なレガシーアプリ。
* 画像認識（OCR / Vision）のみで操作する必要があるアプリ。
* Linux / macOS デスクトップ。
* Web / ブラウザ操作（Playwright の領分）。

## 5. 機能要件（概要）

AI エージェントに公開する主要ツールは以下を想定。詳細仕様は [002\_アーキテクチャ設計.md](002_アーキテクチャ設計.md) の「コマンド定義」参照。

* ウィンドウ / アプリ管理: 一覧取得、アタッチ、クローズ
* 情報取得: Snapshot（軽量 JSON）、スクリーンショット、値取得
* 操作: Click / Fill / Type / Press / Hover / Select
* 制御: 要素出現の待機、任意操作のエスケープハッチ

## 6. 非機能要件

| 区分 | 要件 |
| --- | --- |
| **性能** | Snapshot が AI のコンテキストを圧迫しない粒度で返せる（情報の引き算） |
| **互換性** | 主要な MCP クライアント（Claude Code / Copilot / Cursor / Claude Desktop）から stdio 経由で利用できる |
| **トポロジ** | AI エージェントと同一マシンでもリモートマシンでもテスト対象を扱える |
| **運用** | 接続先の切替が Agent 側設定をいじらず CLI 側で可能 |
| **セキュリティ** | リモート接続時に TLS / 認証トークン等で保護できる余地を残す（初期は最小限） |
| **拡張性** | 将来、別エージェントからも同じバックエンド MCP サーバーを直接参照できる |

## 7. 制約

* Windows のデスクトップセッションに強く依存する（ロック時は動作しない、人間の操作と競合する）。
* UIA 要素の RuntimeId は安定しないため、**セッション内一時 ID（Ref ID）** での参照管理が必須。
* UIA ツリーは膨大になりやすく、そのままでは AI のコンテキストに乗らない。

## 8. 成功の定義（初期）

* Phase 2 完了時: Notepad++ / 電卓を対象に、ADACT CLI 単体で Snapshot / Click / Fill が動く（Engine API レベル、L4 スモーク）。
* Phase 3 完了時: stdio MCP サーバーとして Claude Code 等から ADACT 経由でメモ帳相当の操作ができる。
* Phase 4 完了時: HTTP MCP サーバー (`adact serve`) が daemon として動作する。
* Phase 5 完了時: `adact <subcommand>` の CLI クライアントが daemon に接続して 5 種の操作 (`list-apps` / `attach` / `snapshot` / `click` / `fill`) を実行できる。ローカル直結／リモート接続の両構成をサポートする。

## 9. 設計決定事項（設計フェーズで確定済み）

| 事項 | 決定 |
| --- | --- |
| バックエンド | FlaUI.UIA3 を主、UIA2 fallback 可能にしておく |
| CLI と MCP サーバーの構成 | 分離。**CLI = MCP HTTP クライアント (daemon クライアント)**、MCP サーバー (`adact serve`) はローカル / リモートを選べる ([008](008_要件再整理.md)) |
| Agent↔CLI 通信 | **shell exec** (Coding AI / 人間とも `adact <sub>` を直接実行)。`adact local` (stdio MCP) は他 MCP クライアント (Claude Desktop 等) との互換用に当面残す |
| CLI↔MCPサーバー通信 | Streamable HTTP (MCP) |
| Ref ID ライフサイクル | **snapshot 単位で破棄**（Playwright MCP と同じ方式） |
| Ref ID 形式 | **`s<sessionId>g<generation>e<elementId>`** (例: `s1g3e7`)。世代を埋め込み、古い refId は新 snapshot で即無効化 |
| 並行 Session | **複数 WindowSession を同時保持可能**。Session ID プレフィックスで衝突回避 (`s1e1` と `s2e1` は別物) |
| モーダルダイアログ | 同プロセス + 同 Owner で自動検出し、Snapshot tree に `isModalDialog: true` 付きで含める |
| Phase 2 ターゲットアプリ | **Notepad++ (Win32代表) / 電卓 (UWP代表)** |
| OSS 公開方針 | 初期はプライベート、安定後に OSS 化 |
| .NET ターゲット | **.NET 10 (LTS) / `net10.0-windows`** |
| MCP SDK | **公式 `ModelContextProtocol` C# SDK** (Phase 1-A 結論) |
| Snapshot フィルタ | **`IFilterStrategy` 抽象 + `NodeDecision` 3 値 (Include/Flatten/Exclude)**。Phase 2 既定 2 種 (`operable` / `raw`)、設定・引数化は Phase 6/7 |
| Snapshot メタ情報 | Snapshot JSON に **`_meta`** を必ず付与（filter, sessionId, generation, processName, modalDialog 等） |
| アプリ起動 | Phase 2 では Engine API に含めず、テストで `Process.Start` 直叩き。完成形は **`windows_launch` MCP ツール (Phase 4 or 7)** |
| Phase 2 CLI | **System.CommandLine** 使用、サブコマンドは **`list` / `snapshot` のみ**。click/fill は Engine API として実装し L4 スモークで検証。CLI の本格化は Phase 5 ([008](008_要件再整理.md)) |
| ログ | `Microsoft.Extensions.Logging` を使用、stderr 出力。デフォルト Warning、`--verbose` で Debug |
| 例外 | `AdactException` 基底の独自階層 (`WindowNotFoundException`, `AmbiguousAttachException`, `RefNotFoundException` 等)。MCP 層で標準応答に変換 |
| テスト戦略 | **`.github/skills/testing-strategy/SKILL.md` を SSoT** とし、L1〜L5 の 5 レベル分類で運用 |
| 単一 exe 構造 | `adact.exe` で複数モード: **`adact <sub>` = CLI クライアント (Phase 5)**、`adact local` = stdio MCP server (Phase 3、互換用)、`adact serve` = HTTP MCP daemon (Phase 4)。本体は `Adact.Cli` 1 プロジェクト ([008](008_要件再整理.md)) |
| Phase 3 MCP ツール表面 | **5 種のみ公開**: `windows_list_apps` / `windows_attach` / `windows_snapshot` / `windows_click` / `windows_fill`。`windows_close` は Phase 4、`windows_launch` は Phase 4 or 7、`windows_wait_for` 等は Phase 6 以降 |
| `windows_attach` 引数 | `processName` / `windowTitle` / `className` / `processId` (全て任意、組合せ厳密一致)。複数ヒットは `AMBIGUOUS_ATTACH` エラー |
| Session ハンドリング (MCP) | **ハイブリッド方式**: `windows_attach` が `sessionId` を返し、`windows_snapshot` の `sessionId?` 引数省略時は最後にアタッチした「アクティブ Session」を使用。`windows_click` / `windows_fill` は Ref ID (`s<sid>g<gen>e<eid>`) から Session を一意特定するため `sessionId` 引数は不要。複数 Session 並行可能 |
| MCP エラー応答 | 業務エラー・入力検証エラーは MCP **ツール結果として `isError: true` + 構造化 content (コード + メッセージ)**。JSON-RPC error は transport/protocol 系の systemic エラー専用 |
| Phase 3 エラーコード | `INVALID_ARGUMENT` / `WINDOW_NOT_FOUND` / `AMBIGUOUS_ATTACH` / `REF_NOT_FOUND` / `ELEMENT_INTERACTION_FAILED` / `SNAPSHOT_FAILED` / `FILTER_STRATEGY_NOT_FOUND` / `NO_ACTIVE_SESSION` |
| 自動待機機構 | **γ 案: busy 解除待機 (上限 1000ms、`WaitWhileBusy` 相当) + 50ms スリープフォールバック** を Engine 層 (`ClickAsync` / `FillAsync` 内部) に実装。実装は `Process.WaitForInputIdle` を採用 (両者は実質等価)。MCP 層では追加処理しない。明示 `windows_wait_for` は Phase 6 |
