## 1. 全体構成

### 1.1 基本トポロジ（リモート構成）

```
┌──────────────┐
│  AI Agent    │ (Claude Code / Copilot / Cursor など)
└──────┬───────┘
       │ MCP / stdio (JSON-RPC)
       ▼
┌──────────────┐
│  adact CLI   │ ← MCP プロキシ。Agent 側マシンで動作（必ずローカル）
│ (MCP Proxy)  │
└──────┬───────┘
       │ MCP / Streamable HTTP (or SSE)
       ▼
┌──────────────┐
│ adact serve  │ ← MCP サーバー本体。テスト対象マシンで常駐
│ (MCP Server) │
└──────┬───────┘
       │ FlaUI.UIA3
       ▼
┌──────────────┐
│ Windows UIA3 │ → 対象アプリ
└──────────────┘
```

### 1.2 ローカル構成（層の圧縮）

テスト対象がローカルの場合、CLI とサーバーを 1 プロセスに統合できる。

```
┌──────────────┐
│  AI Agent    │
└──────┬───────┘
       │ MCP / stdio
       ▼
┌──────────────────┐
│ adact local      │ ← MCP サーバーとして振る舞い、同一プロセスで FlaUI 直叩き
└──────┬───────────┘
       │ FlaUI.UIA3
       ▼
┌──────────────┐
│ Windows UIA3 │
└──────────────┘
```

### 1.3 起動モード

| モード | コマンド例 | 役割 | 配置 |
| --- | --- | --- | --- |
| プロキシ（既定） | `adact` | Agent から MCP/stdio を受け、リモート MCP サーバーへ中継 | Agent 側マシン |
| ローカル直結 | `adact local` | プロキシを経由せず同一プロセス内で UIA を実行 | Agent 側マシン（＝テスト対象） |
| サーバー | `adact serve --listen :8080` | MCP サーバーとして常駐。CLI プロキシや他 MCP クライアントから接続を受ける | テスト対象マシン |

## 2. なぜこの構成か（設計判断の記録）

### 2.1 CLI と MCP サーバーを分離する理由

* CLI は **Agent のローカル**でサブプロセスとして動く必要がある（stdio MCP の制約）。
* 一方で、UIA の実行は **テスト対象マシン**で行われる必要があり、物理的に別マシンになり得る。
* この 2 つは論理的に別責務であり、分離することでローカル / リモート構成を統一的に扱える。

### 2.2 両端とも MCP にする理由

* Agent ↔ CLI 間は stdio MCP が事実上必須（Agent 側実装の成熟度）。
* CLI ↔ サーバー間も MCP にしておけば、**将来 Agent が直接サーバーへ接続する構成** も選択肢になる。
* プロトコル再実装のコストを払う必要がない。

### 2.3 CLI プロキシを挟むメリット（対「Agent → リモート MCP 直結」比較）

#### 比較対象

* **案 X (採用)**: Agent → stdio → `adact` CLI(プロキシ) → HTTP → リモート MCP サーバー
* **案 Y (不採用)**: Agent → HTTP → リモート MCP サーバー（直結）

#### 案 X を選ぶ理由

| # | メリット | 内容 |
| --- | --- | --- |
| 1 | **Agent 互換性** | stdio MCP は Claude Code / Copilot / Cursor / Claude Desktop で広く安定。HTTP リモート MCP は Agent 側の対応がまちまちで、stdio に揃えることで全 Agent で動く |
| 2 | **接続先の抽象化** | ローカル / リモート / 複数台の切替を CLI 設定で実現。Agent 側設定（MCP 登録）は触らずに済む |
| 3 | **ローカル fallback** | `local` サブコマンドで同一インターフェースのままプロキシ不要の 1 プロセス運用が可能（層の圧縮） |
| 4 | **認証・秘密情報の分離** | リモート接続に必要なトークン / 証明書を CLI 側で保持。Agent 側の設定ファイルに機密を置かずに済む |
| 5 | **接続の安定化** | 再接続 / リトライ / ハートビートを CLI に集約。Agent の実装品質に依存しない |
| 6 | **ネットワーク層の隠蔽** | SSH トンネル / VPN / mTLS / ポートフォワードを CLI 側で吸収できる |
| 7 | **セキュリティ / 監査** | 実行コマンドのフィルタ・ロギング・レートリミットを CLI で挟める |
| 8 | **人間向けコマンドとの同居** | `adact snapshot --app notepad` 等のデバッグ用 one-shot コマンドを CLI に同居させられる |
| 9 | **ルーティング（将来）** | 複数のテスト対象マシンへリクエストを振り分け可能 |

#### デメリット（案 X）

* プロセス層が 1 つ増える（オーバーヘッドは実用上軽微）
* 実装・保守コストが上乗せ（ただし両側とも MCP なので共通コード化で吸収可）

#### 総合判断

* 開発体験の安定性（Agent 互換性）と運用の柔軟性（接続先抽象化・認証分離）で案 X が上回る。
* 案 Y はシンプルだが Agent 側 HTTP MCP 対応への依存が強く、時期尚早。
* ADACT の要件「CLI はローカル必須・MCP サーバーはリモート可」が案 X で最も自然に満たせる。

### 2.4 バックエンドに FlaUI.UIA3 を採用する理由

#### UIA2 と UIA3 の差異

| 項目 | UIA2 (Managed) | UIA3 (Native COM) |
| --- | --- | --- |
| 実体 | `System.Windows.Automation` | `UIAutomationCore.dll` (COM) |
| 性能 | 古い・遅い場面あり | 高速・機能豊富 |
| 対応範囲 | Win32 / WinForms に安定 | WPF / UWP / WinUI に強い |
| Microsoft 推奨度 | レガシー | 現行推奨 |

#### 候補比較

| 選択肢 | 評価 |
| --- | --- |
| **FlaUI (UIA3/UIA2)** | 本命。COM 隠蔽、`ConditionFactory` / `FindAllDescendants` が強力で情報の引き算を書きやすい。UIA2/UIA3 を同一 API で切替可能 |
| 生 UIA3（COM 直叩き） | 実装・保守コスト大（STA/MTA、手動メモリ管理、難解なキャスト） |
| 生 UIA2 | 古く新アプリに弱い、単独採用は非推奨 |
| UIAComWrapper | FlaUI より低レベル、車輪の再発明寄り |
| WinAppDriver / Appium | WebDriver 層が不要・メンテ停滞気味 |
| AutoIt / TestStack.White 等 | 構造スナップショット弱い、または停滞 |

#### 採用方針

* **FlaUI.UIA3 を主として採用**。
* UIA3 で取得・操作できない要素があった場合の **fallback として FlaUI.UIA2** を選択可能にしておく（FlaUI なら同一 API で切替可能）。
* 採用の最終確認は Phase 1 スパイクで実機検証する。

## 4. コマンド（ツール）定義案

> 公開タイミングは Phase ごとに段階導入する。Phase 3 (stdio MCP 化) で公開するのは下記 4.1 の **5 種のみ**。残りは Phase 4 以降で順次導入する。

### 4.1 Phase 3 で公開するツール

Phase 2 の `Adact.Engine` 機能をそのまま MCP に露出する 5 ツール。

| コマンド | 役割 | 引数 | 戻り値 | 対応 Engine API |
| --- | --- | --- | --- | --- |
| `windows_list_apps` | 実行中アプリとウィンドウの一覧 | (なし) | 配列 (各 `processName` / `windowTitle` / `className` / `processId`) | `ListWindowsAsync` |
| `windows_attach` | 対象ウィンドウにアタッチ (厳密一致、複数ヒット時はエラー) | `processName?` / `windowTitle?` / `className?` / `processId?` (全て任意、組合せ厳密一致) | `{ sessionId, windowInfo }` | `AttachAsync` |
| `windows_snapshot` | アタッチ済 Session の UIA ツリーを軽量 JSON で取得 | `sessionId?` (省略時アクティブ Session) / `filter?` (`operable` / `raw`、省略時 `operable`) | Snapshot JSON (`_meta` + `tree`、§6 のフォーマット) | `SnapshotAsync` |
| `windows_click` | 要素をクリック | `ref` (`s<sid>g<gen>e<eid>`) | 成功時は空応答 | `ClickAsync` |
| `windows_fill` | 入力フィールドに値を設定 (上書き) | `ref`, `value` | 成功時は空応答 | `FillAsync` |

* `windows_click` / `windows_fill` は Ref ID から Session を一意特定できるため `sessionId` 引数を持たない。
* `windows_snapshot` のみ ref を取らないため `sessionId?` 引数を持つ (省略時アクティブ Session)。詳細は §6 「Session ハンドリング (MCP 公開時)」参照。
* サブツリー snapshot (`windows_snapshot` の `ref` 引数) は **Phase 6 で実測ベースに再評価**。Phase 3 では公開しない。

| コマンド | 公開時期 | 役割 | 主な引数 |
| --- | --- | --- | --- |
| `windows_close` | **Phase 4** | 対象ウィンドウを閉じる (実ウィンドウ Close + Detach) | `ref` or `sessionId` |
| `windows_launch` | **Phase 4 or 7** | 指定アプリを起動 (Win32 exe / UWP AppId) | `path` or `appId`, `args` |

| `windows_get_screenshot` | Phase 7 | ウィンドウ / 要素の画像を Base64 PNG で取得 | `ref` |
| `windows_get_value` | 未定 | 値を持つ要素の現在値取得 | `ref` |
| `windows_type` | 未定 | キー入力を 1 文字ずつシミュレート | `ref`, `text` |
| `windows_press` | 未定 | 特定キー / ホットキー押下 | `key` |
| `windows_hover` | 未定 | 要素にマウスホバー | `ref` |

### 4.3 Snapshot 出力フォーマット（案）

```json
[
  {"ref": "w1", "role": "Window", "name": "電卓", "rect": {"x":0,"y":0,"w":400,"h":600}, "children": [
    {"ref": "w2", "role": "Button", "name": "7", "automationId": "num7Button"},
```

## 6. ステート管理方針

### Session と複数ウィンドウ

* `UiaEngine.AttachAsync` は **厳密一致**でウィンドウを特定し `WindowSession` を返す。複数ヒットする場合は例外 (`AmbiguousAttachException`)。曖昧性は `ListWindowsAsync` で先に解消する。
* `WindowSession` は互いに独立。並行に複数保持可能 (例: 電卓と Notepad++ を同時に attach)。
* Ref レジストリは **Session スコープ**で持つ。
* 1 プロセスが複数ウィンドウを持つアプリ (VS Code 等) は、ウィンドウごとに別 Session として attach する。

### Ref ID 形式

* 形式: `s<sessionId>g<generation>e<elementId>` (例: `s1g3e7`)
  * `s<N>`: Session 連番 (UiaEngine インスタンスごとに採番、Detach 後の番号は再利用しない)
  * `g<N>`: Snapshot 世代連番 (Session 内で SnapshotAsync 呼出しごとにインクリメント)
  * `e<N>`: 要素連番 (Snapshot 内で 1 から再採番)
* **Ref レジストリのライフサイクル**: snapshot 単位で破棄。新たな `SnapshotAsync` 呼出し時に旧レジストリをクリアして新世代で再発行する。
* **再利用問題への対策**: 世代を ID に埋め込むことで、古い refId を新 snapshot で使うと「世代不一致」で即 `RefNotFoundException` が発生する。AI が古い ID を誤用しても安全に検知できる。
* `SnapshotResult._meta` に `sessionId` と `generation` を記録。

### モーダルダイアログ検出

* `SnapshotAsync` 実行時、対象 Session の親プロセス配下で「同 Owner Window」かつ「親が WS\_DISABLED」のウィンドウをモーダルダイアログ候補として検出する。
* 検出したモーダルは Snapshot tree (= メインウィンドウ) の **追加子ノード**として挿入し、`isModalDialog: true` フラグを付与。`_meta.modalDialog` にもサマリー情報 (ref, title) を記録する。
  * 設計判断: AI から見て Snapshot ルートは常に「アタッチ対象ウィンドウ単一」のままにしたい (MCP ツールスキーマを単純化したい) ため、`tree` を配列化せず、追加子として混ぜる方式とした。AI は `isModalDialog: true` または `_meta.modalDialog` を見ればモーダル要素を識別できる。
* AI は同じ Snapshot 内の refId でモーダル要素 (OK ボタン等) を操作できる。
* 想定するモーダル: 「保存しますか?」確認、ファイル保存/開くダイアログ、フォント設定ダイアログ、削除確認等。
* 含めない: 親操作可能なフローティングペイン (検索パネル、ツールパレット等)。

### Snapshot JSON フォーマット

ルート構造:

```json
{
  "_meta": {
    "filter": "operable",
    "options": {},
    "generatedAt": "2026-04-25T12:34:56Z",
    "sessionId": "s1",
    "generation": 3,
    "windowTitle": "電卓",
    "processName": "CalculatorApp",
    "processId": 12345,
    "modalDialog": null
  },
  "tree": {
    "ref": "s1g3e1",
    "role": "Window",
    "name": "電卓",
    "automationId": "...",
    "isEnabled": true,
    "boundingRect": [100, 100, 400, 600],
    "children": [
      { "ref": "s1g3e2", "role": "Button", "name": "7", "automationId": "num7Button" }
    ]
  }
}
```

* ネスト構造 (フラットではない)
* `children` は子なしノードでは省略 (キー自体出さない)
* 値が空のキーは省略 (`name: ""` ではなく `name` キーを出さない)
* `boundingRect` は数値配列 `[x, y, w, h]` でサイズ最小化

### Session ハンドリング (MCP 公開時)

Phase 3 で MCP として公開する際の Session 取り扱いは **ハイブリッド方式** を採用する。

* `windows_attach` は新しい Session を作り、`sessionId` (例: `s1`) を結果に含めて返す。
* 以降のツールでの Session 指定は次の通り:
  * `windows_snapshot`: 引数 `sessionId?` を持つ。**省略時は最後にアタッチした Session = アクティブ Session** を使う。アクティブ Session が無い状態で呼ばれた場合は `NO_ACTIVE_SESSION` エラー。
  * `windows_click` / `windows_fill`: `ref` (Ref ID `s<sid>g<gen>e<eid>`) から Session を一意に特定できるため、`sessionId` 引数は持たない。
* 複数 Session を同時にアタッチした場合でも、`ref` ベースのツールは Ref ID プレフィックスで自動的に正しい Session に振り分けられる。
* アクティブ Session の更新タイミング: `windows_attach` 成功時に最新の Session をアクティブとする。明示的な切替ツールは Phase 3 では用意せず、`windows_snapshot` の `sessionId` 引数で都度切替できる。
* Engine 層の `WindowSession` は Phase 2 で複数並行保持を実装済 (§6 「Session と複数ウィンドウ」)。MCP 層はその上に「アクティブ Session」というセッション層の状態を 1 つ追加するだけ。

## 6.5. Snapshot Builder の設計方針

UIA ツリーから Snapshot JSON を生成する際の「どの要素を含めるか／どのプロパティを参照するか」は、アプリケーションや用途によって最適解が揺れる。これを後から差し替えやすい構成にする。

### IFilterStrategy 抽象

```
IFilterStrategy
  string Name { get; }
  NodeDecision Decide(IElement el, FilterContext ctx)         // Include / Flatten / Exclude の3値
  IReadOnlyDictionary<string, object?> ExtractProperties(IElement el)
```

* `NodeDecision` は 3 値 (`Include` / `Flatten` / `Exclude`)。**Flatten は除外しつつ子は親に昇格**させ、構造の連続性を保つ (Phase 1-C の L1.5 相当)。
* プロパティ抽出も戦略側に持たせる。「含めるプロパティのホワイトリスト」を戦略実装が定義する。
* `IElement` は Engine 内部で UIA 要素を抽象化したラッパー。L2 テストで FlaUI を呼ばずに済むよう、必ず抽象化する (詳細はテスト戦略 skill 参照)。

### Phase 2 で実装する戦略 2 種

| 戦略名 | 用途 | 振る舞い |
|---|---|---|
| `operable` (既定) | AI 操作向け | 操作可能要素を中心に残し、無名 Pane / Group は flatten |
| `raw` | デバッグ用 | UIA ツリーをそのまま (フィルタなし) |

### 取得するプロパティ (Phase 2 ホワイトリスト)

| プロパティ | 取得 | 備考 |
|---|---|---|
| `Name` | ✅ | 表示名 |
| `AutomationId` | ✅ | 安定識別子 |
| `ControlType` (`role` として出力) | ✅ | 役割 |
| `ClassName` | ✅ | Win32 識別補助 |
| `IsEnabled` | ✅ | 操作可否 |
| `IsOffscreen` | ✅ | 表示外要素 |
| `Value` | ✅ | 入力欄等 |
| `HelpText` | ✅ | ツールチップ。**無名 Button 対策の要** |
| `BoundingRectangle` | ✅ | 座標・サイズ |
| `IsKeyboardFocusable` | ✅ | フォーカス可否 |
| `HasKeyboardFocus` | ✅ | 現在フォーカス位置 |
| `RuntimeId` | ❌ | UIA の一時 ID。不安定なため Ref ID で代用 |

* 取得失敗時はそのキーを省略 (null は出力しない)。
* Phase 6/7 で必要に応じて追加。

### デフォルト固定 / 拡張余地

* Phase 2 では CLI が既定戦略 (`operable`) を決め打ちする。
* **Phase 3** で MCP ツール `windows_snapshot` に `filter?` 引数を導入し、`operable` / `raw` を切り替えられるようにする (省略時 `operable`)。未登録のフィルタ名を渡した場合は `FILTER_STRATEGY_NOT_FOUND` エラー。
* 設定ファイル化・アプリ別プロファイル自動選択・サードパーティ戦略の追加は Phase 6/7 候補。

### メタ情報の付与 (必須)

Snapshot JSON のルートに `_meta` を必ず含める。AI が「どの視点で見ているか」を認識でき、再現性も担保する。フィールド一覧は §6 「Snapshot JSON フォーマット」参照。

## 6.6. 自動待機機構

click / fill 直後に UI が遷移するケースで、後続の Snapshot / 操作が古い状態を踏まないよう、**Engine 層に最小限の auto-wait** を組み込む。明示的な `windows_wait_for` ツールは Phase 6 で別途実装する。

### 採用方式 (γ 案)

* `WaitWhileBusy` 相当の **busy 解除待機** を行う (上限 1000ms)。具体的には対象アプリの入力キューが処理可能な状態になるまでブロックする。
* 現行実装は `Process.WaitForInputIdle(int)` を採用する。旧 .NET の `System.Windows.Automation.AutomationElement.WaitWhileBusy` も内部で `WaitForInputIdle` を呼んでおり、両者は実質等価。FlaUI.UIA3 が `WaitWhileBusy` を公開していない事情も踏まえ、仕様としては実装手段を限定しない。
* 続けて **最低 50ms のスリープ** を必ず実行する。busy 解除待機が即座に return するアプリでも、メッセージループの整流を 1 ティック分挟む狙い。
* 合計待機時間: 最短 50ms / 最長 1050ms。

### 実装場所

* `WindowSession.ClickAsync` / `WindowSession.FillAsync` の **末尾** で実行 (操作完了後)。
* MCP 層 (Phase 3 以降) は追加の待機を行わず、Engine の auto-wait に任せる。
* `CancellationToken` で中断可能。
* 待機中の例外 (UIA バックエンド異常) は無視して次に進む (auto-wait はベストエフォート)。

### 既知の限界

* busy 解除待機は Win32 / WPF では効きが弱いケースがある (`WaitForInputIdle` / `WaitWhileBusy` いずれを採用しても同じ傾向)。Phase 6 で `windows_wait_for` (条件指定の能動待機) を導入し、AI に明示待機を選ばせる方針。
* 50ms フォールバックは経験的な値。Phase 6 で計測ベースに見直す。

## 7. セキュリティ・運用の初期スコープ

* 初期はローカル / 信頼できる LAN 内を想定。
* リモート接続時は最低限以下を視野に入れる（初期実装は最小）：
  * 接続トークン（共有シークレット）
  * TLS（Streamable HTTP over HTTPS）
  * コマンドホワイトリスト / レートリミット（将来）

### stdio MCP の I/O 分離

* `adact local` (stdio MCP モード) では **stdout は MCP JSON-RPC 専用**。Engine やライブラリが `Console.WriteLine` で stdout に書き込むと即フレーム破壊となる。
* **ログは必ず stderr に出す**。`Microsoft.Extensions.Logging` + `ConsoleLoggerProvider` を stderr 設定で使用 (Phase 2 と同方針、`--verbose` で Debug)。
* テストやデバッグで stdout に出したい一時的な出力も、`local` サブコマンドでは stderr に振り替える。

## 8. エラー応答方式

MCP ツールから返すエラーは **業務エラー** と **systemic エラー** で扱いを分ける。

### ツール結果としてのエラー (`isError: true`)

ADACT のドメインで発生する想定エラー (入力検証失敗、対象未発見、操作失敗など) は MCP ツール結果の **`isError: true` + 構造化 content** として返す。AI クライアントはツールの戻り値として読めるため、リカバリー可能なエラーをハンドリングしやすい。

レスポンス形式 (実装時に詳細決定):

```json
{
  "isError": true,
  "content": [
    { "type": "text", "text": "<CODE>: <message>\nDetails: <JSON>" }
  ]
}
```

### Phase 3 で定義するエラーコード

| コード | 発生条件 | 対応する独自例外 |
| --- | --- | --- |
| `INVALID_ARGUMENT` | 入力検証失敗 (ref 形式不正、必須引数欠如、値の型不正など) | (MCP 層で生成) |
| `WINDOW_NOT_FOUND` | `windows_attach` の対象が見つからない | `WindowNotFoundException` |
| `AMBIGUOUS_ATTACH` | `windows_attach` で複数ヒット | `AmbiguousAttachException` |
| `REF_NOT_FOUND` | ref が世代不一致 / Session 不一致 / malformed | `RefNotFoundException` |
| `ELEMENT_INTERACTION_FAILED` | click / fill 操作失敗 (UIA 操作例外含む) | `ElementInteractionException` |
| `SNAPSHOT_FAILED` | Snapshot 構築失敗 | `SnapshotException` |
| `FILTER_STRATEGY_NOT_FOUND` | `filter` 引数のフィルタ名が未登録 | `FilterStrategyNotFoundException` |
| `NO_ACTIVE_SESSION` | `windows_snapshot` で `sessionId` 省略時にアクティブ Session が無い | (MCP 層で生成) |

### JSON-RPC エラー (systemic)

* transport / protocol レベルのエラー、想定外のシステム例外 (UIA バックエンド突然死、メモリ不足など) は **JSON-RPC エラー (`InternalError` 等)** として返す。
* `AdactException` 以外の例外がツール内で発生した場合、MCP 層で握って `InternalError` に変換する。

### Phase 4 以降の拡張

* リモート接続関連のエラーコード (認証失敗、接続切断、タイムアウト) を Phase 4 で追加。
* CLI プロキシ層のエラーコードを Phase 5 で追加。

## 9. 既知の設計リスク・要検討事項

1. **画面ロック / 人間操作との競合**: UIA は画面ロック時に停止。運用ガイド必要。
2. **スナップショットサイズ**: フィルタ戦略を誤るとコンテキスト枯渇。早期にサイズ計測を入れる。
3. **待機処理**: OS の message loop 的な idle がないため、独自 `wait_for` を正しく設計する必要。
4. **Ref 有効期限**: UI の再描画で対応する要素が失われるケースの扱い。
5. **リモート転送時のスクリーンショット**: Base64 の転送コスト。差分 / 圧縮の余地。
6. **`windows_attach` のエスケープハッチ**: Phase 3 では同 `processId` + 同 `windowTitle` + 同 `className` の組合せが複数存在する極稀ケースを `AMBIGUOUS_ATTACH` で検知して呼び出し側に再試行を促す方針だが、それでも一意化できない場合への保険として `hwnd` を直接受け付ける引数の追加を Phase 6 以降で検討する。
