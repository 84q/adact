# 044: FlaUI 自動テスト生成 Skill 要件定義と設計

## 背景

ADACT の最終目的の 1 つは、AI エージェントが実際に動作する Windows デスクトップアプリケーションを操作・観察し、その結果をもとに再実行可能な自動テストを生成できるようにすることである。

現在の ADACT は、`adact` CLI、daemon、UIA Engine、snapshot / ref モデルを通じて、AI エージェントが Windows アプリを観察・操作するための基盤を備えている。一方で、自然言語シナリオから xUnit / FlaUI の C# テストコードへ落とし込むための作業手順、観察結果の残し方、品質基準、人間が確認すべきポイントはまだ整理されていない。

本ドキュメントでは、将来的な本体機能化の前段として、AI エージェント向け **FlaUI 自動テストコード生成支援 Skill** の要件を定義する。ここで扱うのは Skill としての責務・入出力・ワークフロー方針であり、具体的な実装コードや詳細設計には踏み込みすぎない。

---

## 目的

本 Skill の目的は、自然言語で書かれたテストシナリオと、実際に起動・操作できる Windows アプリケーションを入力に、AI エージェントが ADACT で得た観察結果を利用して、xUnit / FlaUI を用いた C# 自動テストコードの生成を支援することである。

特に次を満たすことを目指す。

- 自然言語シナリオを、検証可能なテストケースへ分解する
- ADACT による操作・観察結果を、テストコード生成に必要な根拠として整理する
- FlaUI でアプリを起動または接続し、安定した UI 要素取得を行う xUnit テストコードを生成する
- 生成コードだけでなく、生成根拠と人間による手動確認ポイントも併せて提示する
- 将来の ADACT 本体機能化に向けた入力・出力・補助機能候補を明確にする

---

## 想定ユーザー

### 第一ユーザー

- AI coding agent / test generation agent
- ADACT を使って Windows アプリを操作・観察する AI エージェント

Skill は、AI エージェントが迷わず観察結果を整理し、テスト設計とコード生成へつなげられることを重視する。

### 第二ユーザー

- Windows デスクトップアプリの開発者・QA 担当者
- FlaUI / xUnit ベースの UI 自動テストを導入したい開発チーム

この層には、生成されたテストコードの妥当性、確認すべきリスク、継続運用に向けた改善余地が分かることが重要である。

---

## 基本ワークフロー

MVP では、**操作・観察フェーズ** と **テスト生成フェーズ** を分離する。

1. ユーザーが自然言語シナリオと対象アプリケーションを提示する
2. AI エージェントが既存の `adact-cli` skill 等を使って対象アプリを起動・接続・操作・観察する
3. 操作手順、画面状態、UI 要素情報、期待結果、失敗・成功表示などを観察結果として整理する
4. FlaUI 自動テスト生成 Skill が観察結果を受け取り、テスト設計方針をまとめる
5. Skill が xUnit / FlaUI の C# テストコードを主成果物として生成する
6. 併せて、生成根拠と人間が確認すべきポイントを提示する

操作しながら順次テストコードを生成する方式は、将来的な拡張候補とする。MVP では、観察結果を一度整理してからコード生成することで、生成根拠の追跡性と人間レビューのしやすさを優先する。

## 入力

### 自然言語シナリオ

自然言語シナリオは、自由文または手順リストを想定する。

例として、次のような粒度を許容する。

- 「アプリを起動し、ユーザー名とパスワードを入力してログインできることを確認する」
- 「設定画面を開き、テーマを Dark に変更し、保存後に表示が変わることを確認する」
- 手順、入力値、期待結果が箇条書きで整理されたテストシナリオ

入力が曖昧な場合、Skill は推奨入力形式を案内できる余地を残す。ただし、MVP では入力形式を厳密に固定せず、AI エージェントが不足情報を観察結果や確認事項として補う方針とする。

### 実際に動作するアプリケーション

対象は、Windows の対話セッション上で起動・操作でき、ADACT / FlaUI で観察可能なアプリケーションとする。

入力としては、次の情報が与えられることを想定する。

- 実行ファイルパス、起動コマンド、または既に起動中のウィンドウ情報
- 必要な起動引数や初期データ
- テストで使用する入力値
- 終了方法やデータ破壊に関する注意事項

ADACT / FlaUI は対話 Windows セッションで動作する必要があるため、サービスセッションなど UI 操作できない環境は対象外とする。

---

## 出力

### 主成果物

主成果物は、xUnit / FlaUI を用いた C# テストコードとする。

生成されるコードは、少なくとも次を満たすことを目指す。

- xUnit のテストとして実行可能である
- FlaUI により対象アプリを起動、または既存プロセス / ウィンドウへ接続できる
- UI 要素を安定して取得する方針が含まれている
- 操作と assertion が自然言語シナリオに対応している

### 補助成果物

テストコードに加えて、次を併せて出力する方針とする。

- 生成根拠: どの観察結果をもとに、どの操作・assertion・selector を採用したか
- 手動確認ポイント: 人間がレビューすべき selector、assertion、テストデータ、起動・終了方法など
- 不確実性: 生成時点で仮定した点、環境依存の可能性がある点、不安定要素

---

## 対象範囲

### 将来的な対象範囲

将来的には、ADACT / FlaUI で操作可能な Windows デスクトップアプリケーション全般を対象とする。

対象候補には、少なくとも次を含める。

- WPF アプリケーション
- WinForms アプリケーション
- Win32 アプリケーション
- UI Automation 経由で十分に観察・操作できるその他の Windows アプリケーション

### MVP の対象範囲

MVP では WPF アプリケーションを主対象とする。

理由は、WPF は UI Automation との相性が比較的よく、AutomationId、Name、ControlType、UIA Pattern などを用いた安定した要素取得方針を立てやすいためである。まず WPF で Skill のワークフロー、観察項目、生成品質基準を固め、その後 WinForms / Win32 などへ展開する。

---

## Skill の責務

FlaUI 自動テスト生成 Skill は、既存の `adact-cli` skill 等で得た観察結果を受け取り、テスト設計とコード生成を支援する。

主な責務は次の通り。

- 自然言語シナリオからテスト観点、操作手順、期待結果を抽出する
- ADACT による観察結果を、テストコード生成に必要な情報へ整理する
- xUnit / FlaUI テストコードの構成方針を提示する
- 安定した selector 候補と、不安定な selector のリスクを整理する
- assertion の候補と、その根拠を明示する
- MVP では直接的なテストコードを主とし、中規模以上では Page Object Model (POM) 化候補や分割方針を提示する
- 生成後に人間が確認すべき点を明示する

一方で、MVP の Skill は ADACT の操作そのものを一手に担うものではない。操作・観察は既存 `adact-cli` skill 等の責務とし、本 Skill はその結果を受け取ってテスト設計・コード生成へつなげる役割を中心にする。

将来的に Skill が巨大化する場合は、次のような分割を検討する。

- シナリオ分析 Skill
- ADACT 観察結果整理 Skill
- FlaUI / xUnit コード生成 Skill
- 生成テストレビュー Skill

---

## 観察結果として残すべき情報

テスト生成の根拠として、操作・観察フェーズでは次の情報を残すことを推奨する。

- 画面情報
  - ウィンドウタイトル
  - 画面遷移
  - 主要領域やダイアログの構造
- 操作手順
  - 実行した操作の順序
  - クリック、入力、選択、待機、スクロールなどの内容
  - 操作に使用した要素 ref や識別情報
- 要素情報
  - AutomationId
  - Name
  - ControlType
  - ClassName
  - Value / Text
  - BoundingRectangle
  - 利用可能な UIA Pattern
- 入力値
  - テキスト入力値
  - 選択項目
  - テストデータや前提データ
- 操作後の状態変化
  - 表示テキストの変化
  - enabled / disabled の変化
  - 選択状態やチェック状態
  - 画面遷移やダイアログ表示
- 期待結果
  - シナリオ上の成功条件
  - UI 上で確認すべき状態
  - 永続化や副作用がある場合の確認観点
- エラー・成功表示
  - エラーメッセージ
  - 成功通知
  - バリデーション表示
- 安定 selector 候補
  - AutomationId ベース
  - Name + ControlType ベース
  - 親子関係や画面コンテキストを組み合わせた候補
- 不安定要素
  - 表示順や座標に依存する要素
  - 動的に変わる Name / Text
  - 固定待ちが必要に見える箇所
  - 仮想化や非同期更新の影響を受ける箇所

## 品質基準

品質基準は、高・中・低の優先度で整理する。

### 高: MVP で必須とする品質

- xUnit のテストとして実行可能である
- FlaUI によるアプリ起動、または既存ウィンドウへの接続ができる
- UI 要素取得が安定している
  - AutomationId が利用できる場合は優先する
  - Name / ControlType / 親子関係などの補助情報を適切に組み合わせる
  - 座標依存や表示順依存を安易に採用しない
- 操作手順が自然言語シナリオと対応している
- 最低限の assertion が含まれている

### 中: 生成品質として重視する項目

- 固定待ちを抑制し、状態待ちや要素待ちを優先する
- assertion がユーザーの期待結果に対応している
- 失敗時に原因を追跡しやすい構成である
  - どの要素取得に失敗したか分かる
  - どの期待結果が満たされなかったか分かる
- テストデータや環境依存値が分離・説明されている
- Page Object Model (POM) 化できる余地がある

### 低: 将来的に適合度を高める項目

- 既存テストプロジェクト構成への適合
- チーム固有の命名規則や fixture 設計への適合
- 共通 helper / base class / POM レイヤーとの統合
- CI 実行時の分類、Trait、並列実行制御への適合

低優先度の項目は重要ではないという意味ではなく、MVP の Skill 要件では汎用性を優先し、個別プロジェクトへの統合は後段の調整対象とする。

---

## POM 化方針

小規模な単発テストでは、テストメソッド内に操作と assertion を直接記述する形を許容する。

一方で、次に該当する場合は Page Object Model (POM) 化を推奨する。

- 同じ画面・要素・操作が複数テストで繰り返される
- 画面遷移やダイアログ操作が複雑である
- 継続運用を前提とするテストである
- selector の変更影響を局所化したい
- テストコードの可読性を保つ必要がある

MVP の Skill は直接コード生成を主成果物とし、POM 化した場合の候補や分割方針は補助情報として提示するに留める。POM コード生成や詳細な構成例は、将来の拡張または reference 側の補助情報として扱う。

---

## 人間の確認ポイント

生成されたテストコードは、最終的に人間が次の観点で確認する必要がある。

- selector の安定性
  - AutomationId が利用できるか
  - Name / Text がローカライズやデータで変動しないか
  - 表示順や座標に依存していないか
- assertion の妥当性
  - 本当にユーザーシナリオの期待結果を検証しているか
  - 表面的な表示確認だけで十分か
  - エラーケースや境界値が別テストとして必要か
- テストデータの環境依存
  - ローカルファイル、DB、ユーザー設定、時刻、ネットワークに依存していないか
  - 実行前後でデータを安全に初期化できるか
- 起動・終了方法の安全性
  - 対象アプリの起動引数が適切か
  - テスト後にプロセスやウィンドウを安全に閉じられるか
  - 未保存データや外部副作用を残さないか
- POM 化すべき重複
  - 同じ selector や操作が複数箇所に散らばっていないか
  - 画面単位・機能単位で抽象化すべき箇所がないか

## 将来の ADACT 本体機能候補

Skill としての運用で得られた知見は、将来的に ADACT 本体機能へ取り込む候補とする。

候補は次の通り。

- 既存の Skill 配布機構の対象に、将来的に FlaUI 自動テスト生成 Skill を追加する拡張検討
- 操作ログ保存
  - 実行した ADACT コマンド
  - snapshot / inspect 結果
  - 操作前後の状態差分
- `snapshot` / `inspect` での安定 selector 候補生成
  - AutomationId 優先度の提示
  - Name / ControlType / 親子関係による代替候補
  - 不安定要素の警告
- 観察結果をテスト生成用に export する形式
- 生成テストの実行補助
- 生成テスト失敗時の解析補助
  - 要素が見つからない原因の推定
  - assertion 失敗時の現在 UI 状態提示
  - snapshot 差分による原因調査

これらは本ドキュメント時点では機能候補であり、確定仕様ではない。

## Requirement フェーズ結論

- FlaUI 自動テスト生成 Skill は、自然言語シナリオと実アプリの観察結果をもとに、xUnit / FlaUI の C# テストコード生成を支援する
- MVP では WPF アプリを主対象とし、操作・観察フェーズとテスト生成フェーズを分離する
- Skill の中心責務は、既存 `adact-cli` skill 等で得た観察結果を受け取り、テスト設計・コード生成・生成根拠・手動確認ポイントへ整理することである
- 主成果物は実行可能な xUnit / FlaUI テストコードとし、生成根拠と不確実性も併せて提示する
- 品質基準は、xUnit 実行可能性、FlaUI による起動・接続、安定した UI 要素取得を最優先とする
- POM 化は常時必須ではなく、MVP では直接コードを主とし、中規模以上や継続運用では POM 化候補・分割方針の提示に留める
- 将来的には、操作ログ保存、安定 selector 候補生成、生成テスト実行・失敗解析補助などを ADACT 本体機能候補として検討する

## Design フェーズ結論

Requirement フェーズの要件を受け、MVP では **`adact-flaui-testgen`** という独立 Skill として設計する。既存 `adact-cli` Skill は Windows アプリの操作・観察を担当し、`adact-flaui-testgen` は観察結果を受け取った後の整理、テスト設計、xUnit / FlaUI の C# テストコード生成支援を担当する。

`adact-flaui-testgen` は ADACT 操作手順そのものを再定義しない。観察結果が不足している場合は、既存 `adact-cli` Skill に戻って追加観察し、その結果を改めてテスト生成入力として扱う。

---

## Design: Skill の位置づけと責務分担

### Skill 名

- Skill 名: `adact-flaui-testgen`
- 位置づけ: ADACT による観察結果をもとに、FlaUI / xUnit の自動テスト生成を支援する Skill
- 既存 Skill との関係: `adact-cli` とは分離する

### `adact-cli` Skill の責務

- 対象 Windows アプリケーションの起動・接続・操作・観察
- snapshot / inspect / screenshot などによる UI 状態の把握
- 操作後の状態変化、UI 要素、失敗状況などの観察

### `adact-flaui-testgen` Skill の責務

- 自然言語シナリオと観察結果の突き合わせ
- テスト対象操作、期待結果、assertion 候補の整理
- 安定 selector 候補と不安定要素の整理
- xUnit / FlaUI の直接操作コード生成支援
- 生成根拠、手動確認ポイント、不確実性、POM 化候補の提示

`adact-flaui-testgen` 自体には、個別の `adact` コマンド詳細を重複記載しない。操作・観察の具体手順は `adact-cli` Skill に委ね、テスト生成側では観察結果として何が必要かを示すに留める。

## Design: 入力と観察結果テンプレート

MVP の入力形式は、厳密なスキーマ強制ではなく推奨テンプレートとする。ただし、将来の補助ツール export 形式を見据え、構造化しやすい項目立てにする。

観察結果テンプレートは標準粒度を基本にし、必要に応じて詳細情報を追加する。

### 標準粒度に含める項目

- シナリオ
- アプリ起動情報
- 画面情報
- 操作手順
- 要素情報
- 状態変化
- 期待結果
- selector 候補
- 不安定要素

### 必要に応じて追加する項目

- snapshot パス
- inspect 結果
- スクリーンショット
- 失敗ログ
- 環境情報

標準粒度は、AI がテスト生成の根拠を説明できる最小限の粒度とする。詳細情報は、selector の安定性判断、非同期更新、失敗原因の追跡など、生成品質に影響する場合に追加する。

## Design: 生成スタイル、起動方式、出力

### 生成スタイル

MVP の生成スタイルは、FlaUI を直接操作する xUnit テストコードとする。POM は次段階の設計対象とし、MVP では POM 化候補の提示に留める。

### 起動方式

生成テストは、ユーザー指定がなければ対象アプリをテストコード側で起動する方式を推奨する。一方で、既に起動中のアプリへ接続する方式にも対応する。

どちらの方式を採用したか、または前提として仮定したかは、生成根拠または不確実性に明記する。

### 出力フォーマット

MVP では、出力の見出しと順序を固定する。

1. 生成したテストコード
2. 生成根拠
3. 手動確認ポイント
4. 不確実性・前提
5. POM 化候補

生成コードだけでなく、なぜその selector、操作、assertion を採用したかを併せて提示することで、人間レビューと修正を容易にする。

## Design: FlaUI / xUnit 生成ガイド方針

FlaUI / xUnit の具体的な書き方、ポイント、注意点は `references/flaui-xunit-guidelines.md` に詳細化する。

生成ガイドは E2E テスト一般の考え方を踏襲する。ただし、ADACT プロジェクト固有のテスト戦略や Layer Trait を、そのまま生成 Skill の標準設計として持ち込むわけではない。生成対象アプリやユーザーの既存テスト基盤に合わせて調整できる余地を残す。

扱う観点は次の通りとする。

- 実行環境依存への注意
- 固定待ちの抑制
- 状態待ち・要素待ちの優先
- cleanup の確実性
- assertion の妥当性
- 失敗時の原因追跡性

## Design: ユーザー確認ルール

ユーザー確認は最小限にする。AI はまず ADACT で観察・試行錯誤し、最も蓋然性が高いテスト生成案まで自律的に進める。

原則として、コード生成前に AI の理解と生成方針を 1 回確認する。ただし、ユーザーが明示的に「テスト生成まで進める」と指示した場合は、その指示に従って生成まで進める。

ユーザーは内部設計やテスト文脈に詳しくない可能性があるため、専門判断を丸投げしない。確認時は、AI が観察結果から判断した方針、残る不確実性、ユーザー判断が必要な理由を短く示す。

### 必ず停止して確認するケース

- 不可逆な副作用があり得る
- 外部送信、課金、通知が発生し得る
- 認証情報・秘密情報を扱う
- テストデータを破壊する可能性がある
- アプリ起動方法が不明で、探索もできない
- 観察結果から複数の業務解釈が同程度に成立し、AI が優先判断できない

## Design: 将来補助ツール候補

将来補助ツール化候補は Skill 本体にも reference にも載せず、本 Design 文書側で目的と入出力イメージを整理する。ここでは具体的な CLI コマンド案までは扱わない。

優先順位は次の通りとする。

### 1. 観察結果 export / 操作ログ保存

- 目的: ADACT による操作・観察の結果を、テスト生成に再利用しやすい形で保存する
- 入力イメージ: 操作ログ、snapshot、inspect 結果、スクリーンショット、シナリオ情報
- 出力イメージ: 観察結果テンプレートに沿った構造化データ

### 2. 安定 selector 候補生成

- 目的: UIA 属性と画面コンテキストから、FlaUI テストで利用しやすい selector 候補を整理する
- 入力イメージ: snapshot、inspect 結果、対象要素、操作目的
- 出力イメージ: 優先 selector、代替 selector、不安定理由、手動確認ポイント

### 3. 生成テストの実行補助

- 目的: 生成された xUnit / FlaUI テストの初回実行と環境依存の確認を支援する
- 入力イメージ: 生成コード、対象アプリ起動情報、テストデータ、実行環境情報
- 出力イメージ: 実行結果、失敗箇所、環境依存の疑い、再観察が必要な項目

### 4. 生成テスト失敗解析補助

- 目的: 要素取得失敗や assertion 失敗の原因を、観察結果と現在 UI 状態から追跡しやすくする
- 入力イメージ: 失敗ログ、現在 snapshot、過去の観察結果、生成根拠
- 出力イメージ: 原因候補、selector 見直し案、待機条件見直し案、追加観察ポイント

## Design フェーズで解消した事項

- Skill は `adact-flaui-testgen` とし、既存 `adact-cli` Skill とは分ける
- `SKILL.md` は入口として小さく保ち、詳細は reference に分割する
- MVP は直接 FlaUI 操作コード生成を主とし、POM は候補提示に留める
- 出力順序は、生成したテストコード、生成根拠、手動確認ポイント、不確実性・前提、POM 化候補で固定する
- 将来補助ツール候補は Skill 本体にも reference にも載せず、Design 文書側で目的と入出力イメージまで整理する
