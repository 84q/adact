## 0. 全体像と各 Phase の対応

ADACT 最終形の階層と、各 Phase が作る部分の対応:

```
┌─────────────────────────────────────────────────┐
│ Agent (Claude Code 等)                           │
└────────────┬────────────────────────────────────┘
             │ stdio + MCP (JSON-RPC)
┌────────────▼────────────────────────────────────┐
│ ① CLI / プロキシ層                                 │  ← Phase 5
│   - `adact` (stdio→HTTP プロキシ)                 │
│   - 起動モード切替                                  │
└────────────┬────────────────────────────────────┘
             │ Streamable HTTP + MCP（リモート時）
┌────────────▼────────────────────────────────────┐
│ ② MCP サーバー層                                   │  ← Phase 3 (stdio) / Phase 4 (HTTP)
│   - windows_snapshot, windows_click 等の          │
│     MCP ツール定義・登録                            │
│   - セッション管理                                   │
└────────────┬────────────────────────────────────┘
             │ 通常の C# メソッド呼び出し
┌────────────▼────────────────────────────────────┐
│ ③ UIA Engine                          ★ Phase 2 ★ │
│   - FlaUI.UIA3 ラッパー                            │
│   - Window アタッチ / 列挙                          │
│   - Snapshot Builder (IFilterStrategy)            │
│   - Ref レジストリ                                   │
│   - click / fill / type 等の操作 API                │
└─────────────────────────────────────────────────┘
                       ↓
              Windows アプリ (UIA)
```

* **Phase 2** で **③ UIA Engine** とその手動検証用の薄い CLI を作り切る（MCP もネットワークも未導入）。
* **Phase 3** で ② を被せて stdio MCP 化、**Phase 4** で HTTP 化、**Phase 5** で ① プロキシを足す積み上げ方式。
* Phase 6/7 は安定化と機能拡張（スクリーンショット / OCR / セレクタ生成など）。

***

## 1. フェーズ分割方針

| Phase | 目的 | 完了条件 |
| --- | --- | --- |
| Phase 1 | スパイク（技術調査・小実験） | MCP SDK の方針確定、FlaUI の動作確認 |
| Phase 2 | UIA 単体プロトタイプ（MCP なし） | メモ帳 / 電卓で Snapshot / Click / Fill が CLI 単体で動く |
| Phase 3 | `adact local` MCP サーバー化 | Claude Code 等から ADACT 経由で操作できる（1 プロセス stdio MCP） |
| Phase 4 | `adact serve` = HTTP MCP サーバー化 | 同じ UIA Engine を HTTP MCP で公開し、他マシンから接続可能 |
| Phase 5 | **CLI クライアント実装** ([008](008_要件再整理.md) で見直し) | `adact <sub>` が daemon に MCP/HTTP で接続し、5 種の操作 (`list-apps`/`attach`/`snapshot`/`click`/`fill`) を実行できる |
| Phase 6 | **Skill 機構** | Coding AI 向け Skill を提供。初期は Phase 5 の 5 サブコマンドをカバー |
| Phase 7 | 安定化 (CLI 拡張以外) | ダイアログ追隨・待機処理洗練・詳細ログ・画面ロック検知・Snapshot サイズ調整 |
| Phase 8 | **サブコマンド拡張 + コマンド体系整理** | `close` / `launch` / `wait-for` / `screenshot` / `hover` / `press` / `type` / `keyboard` / `mouse` 等を Playwright Agent CLI を参考に一括整理 |
| Phase 9+ (候補) | 拡張機能 | Dashboard / OCR / セレクタ生成 / Codegen / state 永続化。採否は Phase 8 完了時に再判断 |

## 2. Phase 1 — スパイク ✅ 完了

**ゴール**: 着手時点で不確実性の高い要素を先に潰し、後続フェーズの前提を確定する。コード量より「調査・実測・判断」が主。

> 結果サマリー: [004\_Phase1A\_MCP\_SDK調査.md](004_Phase1A_MCP_SDK調査.md) / [004\_Phase1B\_FlaUI検証.md](004_Phase1B_FlaUI検証.md) / [004\_Phase1C\_Snapshot計測.md](004_Phase1C_Snapshot計測.md)

### A. MCP SDK の採用判断 ✅

* **目的**: Phase 3 以降の実装コストを確定する。
* **やること**
  * C# 向け MCP SDK の調査（公式 `ModelContextProtocol` NuGet、コミュニティ実装）
  * stdio / Streamable HTTP 両方の対応状況、アクティブなメンテ状況を確認
  * 自前最小実装した場合のスコープと工数をざっくり見積り
* **判断基準**
  * stdio と Streamable HTTP（または SSE）両方を満たせるか
  * ADACT の独自要件（Ref レジストリ等）と衝突しないか
  * 継続メンテナンスの見込み
* **結論**: 公式 `ModelContextProtocol` C# SDK を採用（Apache-2.0、Anthropic+Microsoft 共同メンテ、stdio / Streamable HTTP 両対応）。
* **成果物**: [004\_Phase1A\_MCP\_SDK調査.md](004_Phase1A_MCP_SDK調査.md)

### B. FlaUI / UIA 動作確認スパイク ✅

* **目的**: バックエンドの最終確認。UIA3 主・UIA2 fallback 方針の妥当性検証。
* **やること**
  * **B-1**: FlaUI.UIA3 で Notepad++（Win32 ベースの代表）にアタッチ → ツリー走査 → ボタンクリック
  * **B-2**: FlaUI.UIA3 で電卓（UWP 系）にアタッチ → 同上
  * **B-3**: UIA3 で取得できない要素があったら FlaUI.UIA2 で同じ操作を試して差異を記録
  * ウィンドウ列挙・プロセス指定アタッチの API 確認
* **判断基準**
  * B-1 / B-2 がクラッシュなく動く
  * UIA3 で取れない要素の傾向（ある / ない）を把握
* **結論**: UIA3 単独で OK（電卓・メモ帳・Notepad++ で snapshot / click 成功）。UIA2 fallback は当面不要。**Notepad++ ツールバーの 32 個の Button が Name/AutomationId 共に空**という Win32 特有の落とし穴を発見（Phase 2 で `HelpText` 取得等の対策が必要）。
* **成果物**: [spike/flaui-b/](../spike/flaui-b/) ／ [004\_Phase1B\_FlaUI検証.md](004_Phase1B_FlaUI検証.md)

### C. Snapshot サイズ計測 ✅

* **目的**: 「情報の引き算」ルールのベースライン策定。
* **やること**
  * Notepad++・電卓・エクスプローラで UIA 全ツリーのノード数・JSON サイズを計測
  * フィルタ条件を段階的に変えて差分を測定
    * フィルタなし
    * `ControlType` を操作可能系（Button/Edit/ListItem/Window/Menu/CheckBox/ComboBox）に絞る
    * 名前なし `Pane` / `Group` を除外
* **判断基準**
  * AI のコンテキストに乗る現実的サイズに収まるか（目安: 数 KB〜十数 KB）
  * 極端に大きいアプリでの挙動の見立て
* **結論**: L1〜L1.5 相当のフィルタで全アプリ 22 KB 以下に収まり、目標達成。ただし元仕様の L1 / L2 は同値になることが判明（flatten 処理を入れた L1.5 が実効的）。フィルタ戦略の名称・詳細は Phase 2 で再検討。
* **成果物**: [004\_Phase1C\_Snapshot計測.md](004_Phase1C_Snapshot計測.md)

### 全体の完了条件

* A: MCP SDK の採用方針が決定している
* B: FlaUI.UIA3 で主要アプリが動くことが確認できている（UIA2 fallback の要否を判断）
* C: Snapshot フィルタルール初版と期待サイズの目安が得られている

これらが揃った段階で Phase 2 の具体設計に着手する。

## 3. Phase 2 — UIA 単体プロトタイプ（MCP なし）

**ゴール**: `adact local` の MCP 抜き版。CLI 直接呼び出しで UIA Engine の機能を手動検証できる状態。Phase 3 以降の MCP 化の土台になる UIA Engine を作り切る。

### プロジェクト構成

```
adact.sln
├── src/
│   ├── Adact.Engine/         (クラスライブラリ)
│   └── Adact.Cli/            (実行可能、System.CommandLine)
└── tests/
    └── Adact.Engine.Tests/   (xUnit、L1+L2+L3+L4)
```

* `.NET 10` (LTS) `net10.0-windows`
* 名前空間: `Adact.Engine`, `Adact.Engine.Snapshot`, `Adact.Engine.Filters`, `Adact.Cli`

### Engine API (`Adact.Engine`)

* `UiaEngine` (エントリポイント)
  * `ListWindowsAsync(CancellationToken)` → `IReadOnlyList<WindowInfo>`
  * `AttachAsync(AttachQuery, CancellationToken)` → `WindowSession` (厳密一致、複数ヒットは `AmbiguousAttachException`)
* `WindowSession` (1 ウィンドウへの操作)
  * `SnapshotAsync(SnapshotOptions?, CancellationToken)` → `SnapshotResult` (モーダルダイアログ自動検出含む)
  * `ClickAsync(string refId, ClickOptions?, CancellationToken)`
  * `FillAsync(string refId, string text, CancellationToken)`
  * `Detach()` / `IDisposable.Dispose`
* 全 API は `async Task<T>` + `CancellationToken` を入口で受ける (中身は当面同期可)
* 詳細は [002\_アーキテクチャ設計.md §6](002_アーキテクチャ設計.md) 参照

### Snapshot Builder

* **`IFilterStrategy`** インターフェース (`NodeDecision` 3 値判定 + プロパティ抽出)
* 既定戦略 2 種:
  * `operable` (既定) — 操作可能要素中心、無名 Pane / Group は flatten
  * `raw` (デバッグ用) — フィルタなし
* `IElement` 抽象を切り、FlaUI 直接依存を Engine 内部のラッパー (`FlaUiElement`) に閉じ込める (L2 テストで FakeElement を使うため)
* Ref ID 形式: `s<sessionId>g<generation>e<elementId>` (例: `s1g3e7`)
* Snapshot JSON に `_meta` 必須 (filter, sessionId, generation, windowTitle, processName, modalDialog 等)
* プロパティホワイトリスト: Name / AutomationId / ControlType / ClassName / IsEnabled / IsOffscreen / Value / HelpText / BoundingRectangle / IsKeyboardFocusable / HasKeyboardFocus
* **無名 Button 対策**: `HelpText` (ツールチップ) を必ず取得 (Notepad++ ツールバー等の対策)
* 詳細は [002\_アーキテクチャ設計.md §6 / §6.5](002_アーキテクチャ設計.md) 参照

### 例外設計

* 独自例外型 (`AdactException` 基底)
  * `WindowNotFoundException` / `AmbiguousAttachException` / `RefNotFoundException` / `ElementInteractionException` / `SnapshotException` / `FilterStrategyNotFoundException`
* MCP サーバー層 (Phase 3+) で標準エラー応答に変換する責務を持たせる構造

### CLI (`Adact.Cli`)

* `System.CommandLine` 使用
* Phase 2 サブコマンド: **`list` / `snapshot` のみ** (click/fill は CLI に出さない)
  * `adact list [--json]` — ウィンドウ一覧
  * `adact snapshot --process <name> [--filter operable|raw] [--minified]`
* CLI は手動検証用の薄いラッパー。Phase 3 で MCP に置き換わって役目を終える (一部は開発者用デバッグで残る可能性)

### click / fill の動作確認

* CLI には出さないが Engine API としては Phase 2 で実装する
* 確認は **テストコード (L4 スモーク)** で行う:
  * 電卓 (UWP 代表): 数字ボタンクリック → 表示更新
  * Notepad++ (Win32 代表): メニュー操作 → 期待状態
* テスト準備でアプリ起動は `System.Diagnostics.Process.Start` を直接使用
* 詳細は `.github/skills/testing-strategy/SKILL.md` 参照

### ログ・待機

* `Microsoft.Extensions.Logging` 使用 (`ILogger<T>` をクラスに DI)
* CLI 側で `ConsoleLoggerProvider`、stderr 出力 (stdout は CLI データ用)
* デフォルトレベル: Warning。`--verbose` で Debug
* 待機: 全 API で `CancellationToken` を受ける + Engine 内部に固定タイムアウト (例: 5 秒)
* `WaitForAsync` (明示待機) と Auto-wait は **Phase 6** で実装

### テスト

`.github/skills/testing-strategy/SKILL.md` に従う。Phase 2 では:

| レベル | 取り込み |
|---|---|
| L1 (ユニット) | 必須 — フィルタロジック、Ref レジストリ、JSON 生成、例外 |
| L2 (FakeElement で結合) | 必須 — SnapshotBuilder 主要結合、モーダル検出 |
| L3 (FlaUI 込み結合) | 1 本 — 電卓 |
| L4 (スモーク) | 必須 — 電卓 + Notepad++ |
| L5 (MCP 経由) | — Phase 3 以降 |

### Phase 2 では入れないもの（拡張余地）

* 設定ファイル (YAML/JSON) でのフィルタルール外部記述
* MCP ツール引数によるフィルタ切替
* アプリ別プロファイルの自動選択
* `WaitForAsync` (明示待機) / Auto-wait
* `windows_launch` (アプリ起動) — Phase 6 で MCP ツール化予定
* CLI `--repl` 等の対話モード

### 検証

* L1+L2+L3+L4 のテストがすべて通る
* CLI で `adact list` / `adact snapshot --process notepad++` が動く
* L4 スモークで電卓・Notepad++ が操作できる

### 完了条件

* 上記検証がすべて通る
* Snapshot JSON フォーマットの初版確定 ([002 §6](002_アーキテクチャ設計.md) の通り)
* Phase 3 で MCP サーバー層を被せられる構造で UIA Engine が完成

## 4. Phase 3 — `adact local` MCP サーバー化

**ゴール**: Phase 2 で完成させた `Adact.Engine` を stdio MCP として AI エージェントに公開する。`adact local` 1 プロセスで stdio JSON-RPC + UIA を完結させる。

### プロジェクト構成

```
adact.sln
├── src/
│   ├── Adact.Engine/          (既存)
│   ├── Adact.Mcp.Stdio/       (新規、ライブラリ net10.0-windows)
│   │                          - MCP サーバー実装 + ツール定義
│   └── Adact.Cli/             (既存、`adact local` サブコマンドを追加)
└── tests/
    ├── Adact.Engine.Tests/    (既存、L1〜L4 維持)
    └── Adact.Mcp.Stdio.Tests/ (新規、L5)
```

* 単一 exe (`adact.exe`) で複数モードを切替: 既定 = プロキシ (Phase 5 で実装)、`adact local` = stdio MCP (Phase 3)、`adact serve` = HTTP MCP (Phase 4)。
* Phase 3 では `local` サブコマンドのみ実装 (`serve` は Phase 4)。
* MCP ツール定義は当面 `Adact.Mcp.Stdio` 内に置く。Phase 4 の HTTP 化着手時に共通部の `Adact.Mcp.Common` 抽出を判断する (YAGNI)。

### MCP ツール公開 (5 種)

| ツール | 引数 | 戻り値 | 対応 Engine API |
| --- | --- | --- | --- |
| `windows_list_apps` | (なし) | 配列 (各 `processName` / `windowTitle` / `className` / `processId`) | `ListWindowsAsync` |
| `windows_attach` | `processName?` / `windowTitle?` / `className?` / `processId?` (全て任意、組合せ厳密一致) | `{ sessionId, windowInfo }` | `AttachAsync` |
| `windows_snapshot` | `sessionId?` (省略時アクティブ Session) / `filter?` (`operable` / `raw`、省略時 `operable`) | Snapshot JSON (`_meta` + `tree`) | `SnapshotAsync` |
| `windows_click` | `ref` | 成功時は空応答 | `ClickAsync` |
| `windows_fill` | `ref`, `value` | 成功時は空応答 | `FillAsync` |

詳細仕様は [002\_アーキテクチャ設計.md §4.1](002_アーキテクチャ設計.md) 参照。

### Session ハンドリング

* **ハイブリッド方式** (詳細は [002 §6 「Session ハンドリング (MCP 公開時)」](002_アーキテクチャ設計.md))。
* `windows_attach` 成功時に最新 Session をアクティブ Session として保持。
* `windows_snapshot` のみ `sessionId?` 引数を持ち、省略時アクティブ Session を使用。
* `windows_click` / `windows_fill` は Ref ID プレフィックスから Session を一意特定するため `sessionId` 引数を持たない。
* 複数 Session 並行可能 (Phase 2 で実装済)。

### エラー応答

* 業務エラー・入力検証エラーは MCP **ツール結果として `isError: true` + 構造化 content (コード + メッセージ)**。
* JSON-RPC error は transport / protocol / システム例外 (UIA 突然死等) 専用。
* Phase 3 で定義するエラーコード:
  * `INVALID_ARGUMENT` / `WINDOW_NOT_FOUND` / `AMBIGUOUS_ATTACH` / `REF_NOT_FOUND` / `ELEMENT_INTERACTION_FAILED` / `SNAPSHOT_FAILED` / `FILTER_STRATEGY_NOT_FOUND` / `NO_ACTIVE_SESSION`
* 詳細は [002\_アーキテクチャ設計.md §8](002_アーキテクチャ設計.md) 参照。

### 自動待機機構

* **γ 案: busy 解除待機 (上限 1000ms、`WaitWhileBusy` 相当) + 50ms スリープフォールバック** を Engine 層 (`ClickAsync` / `FillAsync` 内部) に実装。現行実装は `Process.WaitForInputIdle(int)` を採用 (両者は実質等価)。
* MCP 層では追加処理しない。
* 明示的な `windows_wait_for` は Phase 6 で別途実装。
* 詳細は [002\_アーキテクチャ設計.md §6.6](002_アーキテクチャ設計.md) 参照。

### CLI モード

* `adact local` で stdio MCP サーバーとして起動 (stdin/stdout が JSON-RPC、stderr がログ)。
* Phase 2 の `list` / `snapshot` サブコマンドは引き続き利用可 (`adact list` / `adact snapshot --process ...`)。デバッグ用途で残す。
* `adact local --verbose` でログレベルを Debug に。

### ロギング

* Phase 2 と同方針: `Microsoft.Extensions.Logging` + stderr 出力 (`ConsoleLoggerProvider`)。
* デフォルト Warning。`--verbose` で Debug。
* **stdout は MCP JSON-RPC 専用**。Engine やライブラリの `Console.WriteLine` 経由の stdout 汚染を避ける ([002 §7 「stdio MCP の I/O 分離」](002_アーキテクチャ設計.md))。

### テスト

* L5 を新設。`tests/Adact.Mcp.Stdio.Tests/` (xUnit、`[Trait("Layer", "E2E")]`)。
* 公式 `ModelContextProtocol` C# SDK のクライアント API (`ModelContextProtocol.Client` 名前空間) を使用。
* テスト方式: ビルド済 `adact.exe local` を `Process.Start` で spawn → stdio 接続 → JSON-RPC 投げる。
* Phase 3 ケース 1〜2 本:
  * `ListApps_OnRunningSystem_ReturnsNonEmpty` — `windows_list_apps` を呼んで結果が空でないことを確認。
  * `AttachAndSnapshot_OnCalculator_ReturnsTreeWithButtons` — 電卓を起動 → `windows_attach` → `windows_snapshot` → tree に Button が含まれる。
* L1〜L4 (Phase 2 で確立済) は維持。Phase 3 で追加・変更しない。
* テスト方針詳細は `.github/skills/testing-strategy/SKILL.md` 参照。

### Phase 3 では入れないもの（拡張余地）

* `windows_close` (実ウィンドウ Close + Detach) — **Phase 6** で導入
* `windows_detach` (Engine Session のみ解放) — Phase 6 以降
* `windows_launch` — **Phase 6** で導入
* `AttachQuery.Hwnd` 拡張 — **Phase 6** で `windows_close` / `windows_launch` と同時
* サブツリー snapshot (`windows_snapshot` の `ref` 引数) — Phase 6 で実測ベースに再評価
* `windows_wait_for` / `windows_evaluate` — Phase 6
* `windows_get_screenshot` / `windows_get_value` / `windows_type` / `windows_press` / `windows_hover` / `windows_select_option` — Phase 6/7
* HTTP / Streamable HTTP トランスポート — Phase 4
* CLI プロキシ機能 — Phase 5

### 検証

* L1+L2+L3+L4+L5 のテストがすべて green。
* `adact local` を最低 1 つの MCP クライアント (Claude Code 等) から接続し、電卓・Notepad++ を操作できる。

### 完了条件

* 上記検証を通過。
* 最低 1 つの MCP クライアントで安定動作を確認。

## 5. Phase 4 — `adact serve` = HTTP MCP サーバー化

**ゴール**: 同じ UIA Engine を Streamable HTTP の MCP サーバーとして公開する。Phase 4 / 5 は **localhost 限定運用**を前提とし、認証・TLS・CORS は載せない。

### やること

* **`Adact.Mcp.Common` 新規プロジェクトの抽出**: Phase 3 で `Adact.Mcp.Stdio` に置いた `WindowsTools` / `SessionStore` / `ToolErrors` を共通ライブラリへ移動し、stdio / HTTP の双方から参照する。
* **`Adact.Cli` に `serve` サブコマンドを追加**: `adact.exe serve [--port <port>]` で HTTP MCP サーバーを起動。`Adact.Cli` 内部で stdio (`Host.CreateEmptyApplicationBuilder`) と HTTP (`WebApplication.CreateBuilder`) のホストビルダーを分岐。stdio 実装 (`Adact.Mcp.Stdio`) は当面併存させる。
* **Streamable HTTP + ASP.NET Core (Kestrel)**: トランスポートは Streamable HTTP (旧 HTTP+SSE は SDK 上 `[Obsolete]` のため不採用)。ホストは ASP.NET Core + `ModelContextProtocol.AspNetCore` 1.2.0。
* **Stateless モード**: server→client の sampling / elicitation を使わないため、SDK のセッション管理 (Mcp-Session-Id) は扱わない。
* **`127.0.0.1` バインド**: `http://127.0.0.1:<port>` に固定。`0.0.0.0` 既定回避・IPv4 ループバック確実化・ファイアウォールダイアログ抑止・設計意図の明示。
* **`UiaEngine` 層で同時呼び出しを直列化**: `UiaEngine` / `WindowSession` の公開メソッドが共有する `SemaphoreSlim(1, 1)` を導入。SDK はツール呼び出しを直列化しないため、UIA の前面ウィンドウ競合を ADACT 側で防ぐ。
* **SessionStore は Singleton 1 個**: stdio と完全に同じ構成を保つ。
* **`Adact.Cli` の SDK を `Microsoft.NET.Sdk.Web` に変更**: `serve` で ASP.NET Core (Kestrel) を組み込むための必然的な構成変更。
* **コマンド体系の破壊的変更**: `adact --local` フラグを削除し、`adact local` (stdio) / `adact serve` (HTTP) のサブコマンド体系に統一。後方互換は取らない。
* **`serve` のオプションは `--port <int>` のみ**: デフォルトポートは `41300` (ADACT 独自の固定値)。`--listen` / 認証 / TLS 関連オプションは Phase 4 では実装しない。
* **ログ出力は両モードとも stderr に統一**: `Microsoft.Extensions.Logging` の標準パターン (環境変数 `Logging__LogLevel__Default` 等) で制御。
* **MCP `serverInfo.name` / `serverInfo.version` は両モードで `adact` 統一** (バージョンはアセンブリバージョン連動)。
* **テストプロジェクト `Adact.Mcp.Http.Tests` を新規追加**: HTTP MCP の L4 (Smoke) / L5 (E2E) 用。L1 (`SemaphoreSlim` 直列化) は Engine 単体の責務のため `Adact.Engine.Tests/Unit` 配下を維持。

### Phase 4 では入れないもの（拡張余地）

* `windows_close` (実ウィンドウ Close + Detach) — **Phase 6** で導入
* `windows_launch` (Win32 exe / UWP AppId 起動) — **Phase 6** で導入
* `AttachQuery.Hwnd` 拡張 ([005 §6.1](005_Phase3_完了・修正メモ.md)) — **Phase 6** で `windows_close` / `windows_launch` と同時に
* 認証 / TLS / CORS — localhost 限定運用方針のため当面実装しない
* `--listen <addr>:<port>` で 127.0.0.1 以外にバインドする機能
* `--single-client` 起動オプション (同時接続を 1 に絞り、2 つ目以降は 503)

### 検証

* **L1**: `UiaEngine` の `SemaphoreSlim` gate が並列呼び出しを直列化することを mock element で確認
* **L4 (Smoke)**: `Microsoft.AspNetCore.Mvc.Testing.WebApplicationFactory<TEntryPoint>` でインプロセス HTTP サーバーを起動 → SDK の HTTP MCP client で接続 → `windows_list_apps` を 1 回呼ぶ
* **L5 (E2E)**: HTTP 経由で電卓を `windows_attach` + `windows_snapshot`
* **手動疎通**: VS Code Copilot Chat (内蔵 MCP) で stdio + HTTP の両方を確認 ([005 §6.3](005_Phase3_完了・修正メモ.md) の宿題と統合)

### 完了条件

* ビルド成功 (0 warning / 0 error)
* L1 + L2 + L3 + L4 + L5 すべて green
* VS Code Copilot Chat から HTTP + stdio の両方で電卓・メモ帳を操作できること

> 設計詳細は [006\_Phase4\_設計.md](006_Phase4_設計.md) を参照。

## 6. Phase 5 — CLI クライアント実装

**ゴール**: `adact <subcommand>` を Coding AI / 人間が叩く主インターフェースとして提供する ([008](008_要件再整理.md))。Phase 4 で実装した `adact serve` (HTTP MCP daemon) に MCP HTTP クライアントとして接続し、Phase 3 の MCP 5 種と等価な操作を CLI で実行できるようにする。

> [!NOTE]
> 旧 Phase 5 (stdio→HTTP プロキシ) は [008](008_要件再整理.md) で不要化された。Coding AI は CLI を直接 shell exec で叩く前提となり、stdio→HTTP ブリッジは中間層として不要。

> 設計詳細は [009\_Phase5設計.md](009_Phase5設計.md)、実装完了記録は [010\_Phase5\_完了.md](010_Phase5_完了.md) を参照。Phase 5 はスコープ完了 (手動スモーク確認待ち)。

### やること

* CLI サブコマンド実装 (5 種): `list-apps` / `attach` / `snapshot` / `click` / `fill`
* MCP HTTP クライアントとして daemon (`adact serve`) に接続
* 接続先指定方式の設計 (CLI option / 環境変数 / 設定ファイル の組み合わせと優先順位)
* daemon 自動 spawn の有無を判断
* 認証・通信暗号化の初期スコープを判断 (Phase 4 で skip した分の再判断)
* CLI 出力形式 (Page state ヘッダ + snapshot ファイル参照、Playwright Agent CLI モデル)
* エラー出力規約 (exit code、stderr 形式)
* daemon 接続失敗時のメッセージ・対処指示

### 検証

* ローカル daemon 構成で 5 サブコマンドが動く
* リモート daemon 構成 (別マシンに `adact serve` を立てる) でも同じ CLI が動く
* Coding AI (Claude Code 等) から shell exec で `adact` を叩いて電卓・メモ帳を操作できる

### 完了条件

* ローカル・リモートの両構成で同じ CLI コマンドが動く
* 接続先切替が CLI 側設定 (環境変数等) のみで可能
