# ADACT 実装計画

> 前提: [001\_要件定義.md](001_要件定義.md) / [002\_アーキテクチャ設計.md](002_アーキテクチャ設計.md)
> 本書は **何をどの順で作るか** の計画であり、具体コードや詳細 API 仕様は実装フェーズで別途定義する。

## 0. 全体像と各 Phase の対応

ADACT 最終形の階層と、各 Phase が作る部分の対応:

```
┌─────────────────────────────────────────────────┐
│ Agent (Claude Code 等)                           │
└────────────┬────────────────────────────────────┘
             │ stdio + MCP (JSON-RPC)
┌────────────▼────────────────────────────────────┐
│ ① CLI / プロキシ層                                 │  ← Phase 5
│   - `adact` (stdio→HTTP プロキシ)                 │
│   - 起動モード切替                                  │
└────────────┬────────────────────────────────────┘
             │ Streamable HTTP + MCP（リモート時）
┌────────────▼────────────────────────────────────┐
│ ② MCP サーバー層                                   │  ← Phase 3 (stdio) / Phase 4 (HTTP)
│   - windows_snapshot, windows_click 等の          │
│     MCP ツール定義・登録                            │
│   - セッション管理                                   │
└────────────┬────────────────────────────────────┘
             │ 通常の C# メソッド呼び出し
┌────────────▼────────────────────────────────────┐
│ ③ UIA Engine                          ★ Phase 2 ★ │
│   - FlaUI.UIA3 ラッパー                            │
│   - Window アタッチ / 列挙                          │
│   - Snapshot Builder (IFilterStrategy)            │
│   - Ref レジストリ                                   │
│   - click / fill / type 等の操作 API                │
└─────────────────────────────────────────────────┘
                       ↓
              Windows アプリ (UIA)
```

* **Phase 2** で **③ UIA Engine** とその手動検証用の薄い CLI を作り切る（MCP もネットワークも未導入）。
* **Phase 3** で ② を被せて stdio MCP 化、**Phase 4** で HTTP 化、**Phase 5** で ① プロキシを足す積み上げ方式。
* Phase 6/7 は安定化と機能拡張（スクリーンショット / OCR / セレクタ生成など）。

***

## 1. フェーズ分割方針

| Phase | 目的 | 完了条件 |
| --- | --- | --- |
| Phase 1 | スパイク（技術調査・小実験） | MCP SDK の方針確定、FlaUI の動作確認 |
| Phase 2 | UIA 単体プロトタイプ（MCP なし） | メモ帳 / 電卓で Snapshot / Click / Fill が CLI 単体で動く |
| Phase 3 | `--local` MCP サーバー化 | Claude Code 等から ADACT 経由で操作できる（1 プロセス stdio MCP） |
| Phase 4 | `adact serve` = HTTP MCP サーバー化 | 同じ UIA Engine を HTTP MCP で公開し、他マシンから接続可能 |
| Phase 5 | `adact` プロキシ（stdio→HTTP ブリッジ） | 別マシンのテスト対象を Agent から操作できる |
| Phase 6 | 安定化 | ダイアログ追随・待機処理洗練・詳細ログ・画面ロック検知 |
| Phase 7 | 拡張機能 | スクリーンショット / OCR / セレクタ生成 / テスト生成 |

## 2. Phase 1 — スパイク ✅ 完了

**ゴール**: 着手時点で不確実性の高い要素を先に潰し、後続フェーズの前提を確定する。コード量より「調査・実測・判断」が主。

> 結果サマリー: [004\_Phase1A\_MCP\_SDK調査.md](004_Phase1A_MCP_SDK調査.md) / [004\_Phase1B\_FlaUI検証.md](004_Phase1B_FlaUI検証.md) / [004\_Phase1C\_Snapshot計測.md](004_Phase1C_Snapshot計測.md)

### A. MCP SDK の採用判断 ✅

* **目的**: Phase 3 以降の実装コストを確定する。
* **やること**
  * C# 向け MCP SDK の調査（公式 `ModelContextProtocol` NuGet、コミュニティ実装）
  * stdio / Streamable HTTP 両方の対応状況、アクティブなメンテ状況を確認
  * 自前最小実装した場合のスコープと工数をざっくり見積り
* **判断基準**
  * stdio と Streamable HTTP（または SSE）両方を満たせるか
  * ADACT の独自要件（Ref レジストリ等）と衝突しないか
  * 継続メンテナンスの見込み
* **結論**: 公式 `ModelContextProtocol` C# SDK を採用（Apache-2.0、Anthropic+Microsoft 共同メンテ、stdio / Streamable HTTP 両対応）。
* **成果物**: [004\_Phase1A\_MCP\_SDK調査.md](004_Phase1A_MCP_SDK調査.md)

### B. FlaUI / UIA 動作確認スパイク ✅

* **目的**: バックエンドの最終確認。UIA3 主・UIA2 fallback 方針の妥当性検証。
* **やること**
  * **B-1**: FlaUI.UIA3 で Notepad++（Win32 ベースの代表）にアタッチ → ツリー走査 → ボタンクリック
  * **B-2**: FlaUI.UIA3 で電卓（UWP 系）にアタッチ → 同上
  * **B-3**: UIA3 で取得できない要素があったら FlaUI.UIA2 で同じ操作を試して差異を記録
  * ウィンドウ列挙・プロセス指定アタッチの API 確認
* **判断基準**
  * B-1 / B-2 がクラッシュなく動く
  * UIA3 で取れない要素の傾向（ある / ない）を把握
* **結論**: UIA3 単独で OK（電卓・メモ帳・Notepad++ で snapshot / click 成功）。UIA2 fallback は当面不要。**Notepad++ ツールバーの 32 個の Button が Name/AutomationId 共に空**という Win32 特有の落とし穴を発見（Phase 2 で `HelpText` 取得等の対策が必要）。
* **成果物**: [spike/flaui-b/](../spike/flaui-b/) ／ [004\_Phase1B\_FlaUI検証.md](004_Phase1B_FlaUI検証.md)

### C. Snapshot サイズ計測 ✅

* **目的**: 「情報の引き算」ルールのベースライン策定。
* **やること**
  * Notepad++・電卓・エクスプローラで UIA 全ツリーのノード数・JSON サイズを計測
  * フィルタ条件を段階的に変えて差分を測定
    * フィルタなし
    * `ControlType` を操作可能系（Button/Edit/ListItem/Window/Menu/CheckBox/ComboBox）に絞る
    * 名前なし `Pane` / `Group` を除外
* **判断基準**
  * AI のコンテキストに乗る現実的サイズに収まるか（目安: 数 KB〜十数 KB）
  * 極端に大きいアプリでの挙動の見立て
* **結論**: L1〜L1.5 相当のフィルタで全アプリ 22 KB 以下に収まり、目標達成。ただし元仕様の L1 / L2 は同値になることが判明（flatten 処理を入れた L1.5 が実効的）。フィルタ戦略の名称・詳細は Phase 2 で再検討。
* **成果物**: [004\_Phase1C\_Snapshot計測.md](004_Phase1C_Snapshot計測.md)

### 全体の完了条件

* A: MCP SDK の採用方針が決定している
* B: FlaUI.UIA3 で主要アプリが動くことが確認できている（UIA2 fallback の要否を判断）
* C: Snapshot フィルタルール初版と期待サイズの目安が得られている

これらが揃った段階で Phase 2 の具体設計に着手する。

## 3. Phase 2 — UIA 単体プロトタイプ（MCP なし）

**ゴール**: `adact --local` の MCP 抜き版。CLI 直接呼び出しで UIA Engine の機能を手動検証できる状態。Phase 3 以降の MCP 化の土台になる UIA Engine を作り切る。

### プロジェクト構成

```
adact.sln
├── src/
│   ├── Adact.Engine/         (クラスライブラリ)
│   └── Adact.Cli/            (実行可能、System.CommandLine)
└── tests/
    └── Adact.Engine.Tests/   (xUnit、L1+L2+L3+L4)
```

* `.NET 10` (LTS) `net10.0-windows`
* 名前空間: `Adact.Engine`, `Adact.Engine.Snapshot`, `Adact.Engine.Filters`, `Adact.Cli`

### Engine API (`Adact.Engine`)

* `UiaEngine` (エントリポイント)
  * `ListWindowsAsync(CancellationToken)` → `IReadOnlyList<WindowInfo>`
  * `AttachAsync(AttachQuery, CancellationToken)` → `WindowSession` (厳密一致、複数ヒットは `AmbiguousAttachException`)
* `WindowSession` (1 ウィンドウへの操作)
  * `SnapshotAsync(SnapshotOptions?, CancellationToken)` → `SnapshotResult` (モーダルダイアログ自動検出含む)
  * `ClickAsync(string refId, ClickOptions?, CancellationToken)`
  * `FillAsync(string refId, string text, CancellationToken)`
  * `Detach()` / `IDisposable.Dispose`
* 全 API は `async Task<T>` + `CancellationToken` を入口で受ける (中身は当面同期可)
* 詳細は [002\_アーキテクチャ設計.md §6](002_アーキテクチャ設計.md) 参照

### Snapshot Builder

* **`IFilterStrategy`** インターフェース (`NodeDecision` 3 値判定 + プロパティ抽出)
* 既定戦略 2 種:
  * `operable` (既定) — 操作可能要素中心、無名 Pane / Group は flatten
  * `raw` (デバッグ用) — フィルタなし
* `IElement` 抽象を切り、FlaUI 直接依存を Engine 内部のラッパー (`FlaUiElement`) に閉じ込める (L2 テストで FakeElement を使うため)
* Ref ID 形式: `s<sessionId>g<generation>e<elementId>` (例: `s1g3e7`)
* Snapshot JSON に `_meta` 必須 (filter, sessionId, generation, windowTitle, processName, modalDialog 等)
* プロパティホワイトリスト: Name / AutomationId / ControlType / ClassName / IsEnabled / IsOffscreen / Value / HelpText / BoundingRectangle / IsKeyboardFocusable / HasKeyboardFocus
* **無名 Button 対策**: `HelpText` (ツールチップ) を必ず取得 (Notepad++ ツールバー等の対策)
* 詳細は [002\_アーキテクチャ設計.md §6 / §6.5](002_アーキテクチャ設計.md) 参照

### 例外設計

* 独自例外型 (`AdactException` 基底)
  * `WindowNotFoundException` / `AmbiguousAttachException` / `RefNotFoundException` / `ElementInteractionException` / `SnapshotException` / `FilterStrategyNotFoundException`
* MCP サーバー層 (Phase 3+) で標準エラー応答に変換する責務を持たせる構造

### CLI (`Adact.Cli`)

* `System.CommandLine` 使用
* Phase 2 サブコマンド: **`list` / `snapshot` のみ** (click/fill は CLI に出さない)
  * `adact list [--json]` — ウィンドウ一覧
  * `adact snapshot --process <name> [--filter operable|raw] [--minified]`
* CLI は手動検証用の薄いラッパー。Phase 3 で MCP に置き換わって役目を終える (一部は開発者用デバッグで残る可能性)

### click / fill の動作確認

* CLI には出さないが Engine API としては Phase 2 で実装する
* 確認は **テストコード (L4 スモーク)** で行う:
  * 電卓 (UWP 代表): 数字ボタンクリック → 表示更新
  * Notepad++ (Win32 代表): メニュー操作 → 期待状態
* テスト準備でアプリ起動は `System.Diagnostics.Process.Start` を直接使用
* 詳細は `.github/skills/testing-strategy/SKILL.md` 参照

### ログ・待機

* `Microsoft.Extensions.Logging` 使用 (`ILogger<T>` をクラスに DI)
* CLI 側で `ConsoleLoggerProvider`、stderr 出力 (stdout は CLI データ用)
* デフォルトレベル: Warning。`--verbose` で Debug
* 待機: 全 API で `CancellationToken` を受ける + Engine 内部に固定タイムアウト (例: 5 秒)
* `WaitForAsync` (明示待機) と Auto-wait は **Phase 6** で実装

### テスト

`.github/skills/testing-strategy/SKILL.md` に従う。Phase 2 では:

| レベル | 取り込み |
|---|---|
| L1 (ユニット) | 必須 — フィルタロジック、Ref レジストリ、JSON 生成、例外 |
| L2 (FakeElement で結合) | 必須 — SnapshotBuilder 主要結合、モーダル検出 |
| L3 (FlaUI 込み結合) | 1 本 — 電卓 |
| L4 (スモーク) | 必須 — 電卓 + Notepad++ |
| L5 (MCP 経由) | — Phase 3 以降 |

### Phase 2 では入れないもの（拡張余地）

* 設定ファイル (YAML/JSON) でのフィルタルール外部記述
* MCP ツール引数によるフィルタ切替
* アプリ別プロファイルの自動選択
* `WaitForAsync` (明示待機) / Auto-wait
* `windows_launch` (アプリ起動) — Phase 4 or 7 で MCP ツール化予定
* CLI `--repl` 等の対話モード

### 検証

* L1+L2+L3+L4 のテストがすべて通る
* CLI で `adact list` / `adact snapshot --process notepad++` が動く
* L4 スモークで電卓・Notepad++ が操作できる

### 完了条件

* 上記検証がすべて通る
* Snapshot JSON フォーマットの初版確定 ([002 §6](002_アーキテクチャ設計.md) の通り)
* Phase 3 で MCP サーバー層を被せられる構造で UIA Engine が完成

## 4. Phase 3 — `--local` MCP サーバー化

**ゴール**: Phase 2 の機能を stdio MCP として公開。1 プロセス構成で AI エージェントから呼び出せる。

### やること

* stdio トランスポート実装
* Phase 2 の機能を MCP ツールとして登録（`windows_snapshot` 等）
* ツールスキーマの記述
* エラー応答の統一フォーマット
* セッション / Ref レジストリの整備
* **最小の待機機構**（click 直後の遷移を待てる程度）を導入

### 検証

* Claude Code / もう 1 つの MCP クライアントに登録し、メモ帳を AI から操作

### 完了条件

* 最低 2 つの MCP クライアントで安定動作を確認

## 5. Phase 4 — `adact serve` = HTTP MCP サーバー化

**ゴール**: 同じ UIA Engine を Streamable HTTP の MCP サーバーとして公開する。

### やること

* `adact serve --listen :PORT` の起動モード実装
* Streamable HTTP（または SSE）トランスポート実装
* 認証トークン・TLS の最小対応
* UIA Engine の共有（Phase 3 の stdio と同一コードを使い回す構造に整理）
* **`windows_launch` MCP ツールの追加検討**: アプリ起動 (Win32 exe / UWP AppId)。Phase 7 への先送りも可。

### 検証

* 任意の MCP HTTP クライアントから `adact serve` に接続してメモ帳を操作

### 完了条件

* HTTP MCP クライアントから Phase 3 と同等の操作ができる

## 6. Phase 5 — `adact` プロキシ（stdio→HTTP ブリッジ）

**ゴール**: Agent ↔ CLI は stdio MCP、CLI ↔ Server は HTTP MCP の 2 段構成を実現。

### やること

* `adact` 既定モード: Agent からの stdio MCP を上位 HTTP MCP サーバーへ中継
* 接続設定（接続先 URL、トークン、TLS）
* 再接続 / ハートビート
* 3 モード（`adact` / `adact --local` / `adact serve`）の共通コード整理

### 検証

* マシン A（Agent + `adact`）→ マシン B（`adact serve`）の構成でメモ帳操作

### 完了条件

* ローカル・リモートの両構成で同じ Agent 設定のまま動く

## 7. Phase 6 — 安定化

**ゴール**: E2E で安定動作するレベルまで仕上げる。

### やること

* `windows_wait_for` の本格実装（要素出現 / 消失 / 新ウィンドウ検知）
* モーダルダイアログ検出と自動追随
* 失敗時の詳細ログ（スクリーンショット添付等）
* 画面ロック時の明示的エラー
* Snapshot サイズのチューニング
* 構造化ログ基盤（Serilog 等）の本格整備

## 8. Phase 7 — 拡張機能

**ゴール**: 差別化となる機能群の追加。

### 候補

* `windows_get_screenshot`（Base64 PNG 返却）
* OCR 連携（UIA 非対応箇所のテキスト抽出）
* 安定セレクタ生成（AutomationId + Name + ControlType の組合せ提案）
* テストコード自動生成（Playwright Codegen 相当）
* ステートの永続化（ログイン済み状態の保存・復旧、要検討）
