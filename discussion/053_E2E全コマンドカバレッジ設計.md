# 053 — E2E 全コマンドカバレッジ設計

## 1. 目的

ID 27「全サブコマンド自動統合テスト化」に対する設計を整理する。

本タスクでは、**CLI に登録済みの全サブコマンド（`serve` 系含む）を E2E でカバーする**。
ただし 1 本の巨大シナリオにはせず、**失敗箇所を切り分けやすい複数シナリオ**へ分割する。

## 2. 前提と合意事項

### 2.1 テストレベル

- 実装前提は **CLI E2E 中心** とする
- `serve http` / `serve pipe` のように CLI 単体では自己観測しづらいもの、または transport 差分の確認が必要なものは、**必要に応じて HTTP E2E で補完**する
- Layer は `Trait("Layer", "E2E")` を基本とする

### 2.2 対象範囲

- 対象は **正常系のみ** とする
- 異常系、権限不足、interactive session 不在、接続失敗、タイムアウト発生時の分岐は今回の対象外
- 対象アプリは **特段理由がない限り SampleApp に統一**する
- `kill` は **`launch` とセット**で、テスト専用に起動した別プロセスを対象にする

### 2.3 成功判定の考え方

厳密な画面一致は採用しない。代わりに、各コマンドの成功を以下のいずれかで確認する。

- snapshot 上で状態変化を確認できる
- `inspect` 結果で属性を確認できる
- `screenshot` / `install` などの生成物を確認できる
- `wait-for-*` の完了を確認できる
- `close-window` / `kill` / `daemon-stop` などのプロセス・ウィンドウ終了を確認できる

### 2.4 flaky 対策

- **全待機系 (`wait-for-element`, `wait-for-window` を含む) で明示 timeout を必須**とする
- 無限待機を避けるため、polling ベースの補助待機にも上限時間を付ける
- flaky 対策リトライは **初回実装では入れない**

## 3. 対象コマンド一覧

現行の CLI 登録済みコマンドを対象とする。

### 3.1 共有コマンド

`list-windows`, `attach`, `snapshot`, `click`, `fill`, `doubleclick`, `hover`, `mousemove`, `mousedown`, `mouseup`, `mousewheel`, `keypress`, `keydown`, `keyup`, `type`, `check`, `uncheck`, `select`, `focus`, `scroll-into-view`, `scroll`, `resize-window`, `minimize-window`, `maximize-window`, `restore-window`, `inspect`, `screenshot`, `wait-for-element`, `wait-for-window`, `detach`, `close-window`, `kill`

### 3.2 その他のルートコマンド

`install`, `launch`, `daemon-stop`, `serve http`, `serve pipe`

## 4. シナリオ分割方針

- 1 シナリオ 1 責務を原則とする
- 失敗時に「接続」「基本操作」「入力」「待機」「プロセス管理」のどこで落ちたかを切り分けやすくする
- 可能な限り **各シナリオは独立実行可能**にする
- 参照 ref は固定文字列に依存しすぎず、必要に応じて各シナリオ冒頭の snapshot / inspect で取り直す

## 5. シナリオ設計

### S01. サーバ起動・接続基盤

- **対象コマンド**: `serve pipe`, `serve http`, `list-windows`, `attach`, `snapshot`, `daemon-stop`
- **目的**: 全 E2E の前提となる transport と基本接続が成立することを確認する
- **成功判定**:
  - `serve pipe` / `serve http` でサーバプロセスが起動する
  - `list-windows` で SampleApp が列挙される
  - `attach` 後に session が払い出される
  - `snapshot` で SampleApp のツリーが取得できる
  - `daemon-stop` 後に対象 daemon プロセスが終了する
- **注意**:
  - `serve` 系は長寿命プロセスのため、CLI E2E で起動し、必要に応じて HTTP E2E から疎通確認を補完する
  - `daemon-stop` は **local / Named Pipe daemon 専用**であり、HTTP モード (`serve http`) の停止には使わない
  - `daemon-stop` は stop 対象 daemon を `serve pipe` で専用起動し、他シナリオと共有しない

### S02. 基本参照・観測

- **対象コマンド**: `snapshot`, `inspect`, `screenshot`, `focus`, `hover`
- **目的**: 観測系コマンドが SampleApp 上で安定して使えることを確認する
- **成功判定**:
  - `snapshot` に期待タブまたは代表要素が含まれる
  - `inspect` が対象要素の `name` / `controlType` / `automationId` などを返す
  - `screenshot` で PNG が生成される
  - `focus` 実行後、snapshot または inspect で対象要素が focused になる
  - `hover` がエラーなく完了する
- **注意**:
  - `hover` は視覚変化に依存せず、成功応答と後続操作継続可能性で判定する

### S03. テキスト入力・キー操作

- **対象コマンド**: `fill`, `type`, `keypress`, `keydown`, `keyup`
- **目的**: 文字入力経路と低レベルキー入力経路を分けて確認する
- **成功判定**:
  - `fill` 後に TextBox の値が更新される
  - `type` 後に追加入力分が反映される
  - `keypress` で Tab 移動など観測可能な変化が起きる
  - `keydown` + `keyup` は専用入力欄または修飾キーを伴う操作に使い、結果が UI 上で確認できる
- **注意**:
  - `keydown` / `keyup` 単独成功は観測しにくいため、**意味のある組み合わせ操作**として検証する
  - 文字列一致は完全一致よりも「期待トークンが含まれる」で十分な箇所を選ぶ

### S04. 選択・トグル操作

- **対象コマンド**: `click`, `check`, `uncheck`, `select`
- **目的**: 典型的な要素操作を SampleApp の安定部品で確認する
- **成功判定**:
  - `click` でボタン押下後の状態変化が確認できる
  - `check` / `uncheck` で CheckBox 状態が切り替わる
  - `select` で ComboBox または List の選択結果が UI 上で確認できる
- **注意**:
  - 選択結果は見えにくい場合があるため、対象コントロールは snapshot に value / selected item が出るものを優先する

### S05. マウス操作・スクロール

- **対象コマンド**: `doubleclick`, `mousemove`, `mousedown`, `mouseup`, `mousewheel`, `scroll-into-view`, `scroll`
- **目的**: 低レベルマウス操作とスクロール系を 1 つの UI 領域で検証する
- **成功判定**:
  - `doubleclick` 後に DataGrid / List / Tree などで観測可能な状態変化が起きる
  - `mousemove`, `mousedown`, `mouseup` は後続の選択・ドラッグ準備・フォーカス変化などに結び付けて確認する
  - `mousewheel` または `scroll` 後に表示項目が変わる、または `scroll-into-view` 対象が snapshot に現れる
  - `scroll-into-view` 後に対象行・項目が観測可能になる
- **注意**:
  - 低レベルマウス操作は単独では判定しにくいため、**連続操作として設計**する
  - `mousewheel` と `scroll` は別 API 経路のため別コマンドとして両方保持する

### S06. ウィンドウ状態変更

- **対象コマンド**: `resize-window`, `minimize-window`, `maximize-window`, `restore-window`
- **目的**: ウィンドウ操作系をまとめて確認する
- **成功判定**:
  - `maximize-window` / `restore-window` / `minimize-window` が成功する
  - `resize-window` 後に window size が inspect または後続 snapshot から確認できる
  - `minimize-window` 後は必要に応じて `restore-window` して以降のシナリオへ影響を残さない
- **注意**:
  - 最小化中は一部操作が失敗しうるため、**このシナリオ内で `restore-window` まで完結**させる

### S07. 待機系

- **対象コマンド**: `wait-for-element`, `wait-for-window`
- **目的**: 明示 timeout 付き待機が正常に完了することを確認する
- **成功判定**:
  - `wait-for-element` が SampleApp の遅延 UI 変化に対して timeout 内で成功する
  - `wait-for-window` が SampleApp の子ウィンドウ表示を timeout 内で検出する
- **注意**:
  - **全呼び出しで timeout を明示**する
  - 変化源は SampleApp の `Async / Delay` タブ（AutomationId: `MainWindow_TabItem_AsyncDelay`）、`Multi-Window` タブを優先する
  - 無限待機回避のため、補助的な待機も同一の上限時間ポリシーに揃える

### S08. セッション解放とウィンドウ終了

- **対象コマンド**: `detach`, `close-window`
- **目的**: セッションと UI ウィンドウの終了経路を分けて確認する
- **成功判定**:
  - `detach` 後、同一ウィンドウへ再 `attach` できる
  - `close-window` 後、対象ウィンドウが `list-windows` から消える、または再 attach 不可になる
- **注意**:
  - `close-window` は SampleApp 本体を閉じると後続へ影響するため、専用起動した SampleApp インスタンスで行う

### S09. プロセス起動・強制終了

- **対象コマンド**: `launch`, `kill`
- **目的**: アプリ起動と kill のライフサイクルを専用プロセスで確認する
- **成功判定**:
  - `launch` で対象プロセスが起動し、`list-windows` または PID 確認で存在が分かる
  - 起動したプロセスへ attach できる
  - `kill` 後に対象プロセスが終了し、再利用されていないことを確認できる
- **注意**:
  - **`kill` は `launch` で起動した専用プロセスだけを対象**にする
  - SampleApp を優先するが、起動容易性や終了判定の都合で別プロセスを使う合理性がある場合のみ例外を認める

### S10. install コマンド

- **対象コマンド**: `install`
- **目的**: GUI 操作以外のルートコマンドも E2E 対象に含める
- **成功判定**:
  - 一時ディレクトリを cwd にして `install --skills <client>` を実行し、client ごとの skills root 配下に `adact-cli/` と `adact-flaui-testgen/` が生成される
  - 例: `codex` なら `.agents/skills/adact-cli/` と `.agents/skills/adact-flaui-testgen/`、`claude` なら `.claude/skills/adact-cli/` と `.claude/skills/adact-flaui-testgen/` が生成される
  - `SKILL.md` と `references/*.md` など主要ファイル内容、または最低限のディレクトリ構成が確認できる
  - CLI 成功出力の `path` が individual Skill ディレクトリではなく、client 別 skills root（例: `codex` なら `.agents/skills`）を返すことを確認できる
- **注意**:
  - 現行 CLI では `install` 単独実行は不可で、**`install --skills <copilot|claude|codex>` 形式で `--skills` 指定が必須**
  - UI 確認ではなく **ファイル生成確認**で成功判定する
  - 非 `--global` 時の install 先は任意指定ではなく **実行時 cwd 配下の client ごとの規定相対パス**（例: `codex` → `.agents/skills`, `claude` → `.claude/skills`, `copilot` → `.github/skills`）であり、生成物はその root 直下のファイルではなく **各 Skill サブディレクトリ**（`adact-cli/`, `adact-flaui-testgen/`）として配置される
  - E2E では **`--global` を使わず**、テストごとの一時ディレクトリを cwd にして実行し、上記の client ごとの相対配置先を確認して既存ユーザ設定へ影響しないようにする

## 7. 実装時の補助方針

- 既存の E2E / Smoke 用 fixture, `InteractiveTestGuard`, 共通 helper を再利用する
- daemon 起動、CLI 実行、snapshot 保存先、一時ディレクトリ、後始末を fixture に寄せる
- 失敗解析しやすいよう、各シナリオは実行 CLI と生成物パスをテスト出力へ残す
- SampleApp 側の UI 差分で不安定になりやすい箇所は避け、discussion/032 で比較的安定だった経路を優先する

## 8. 今回あえて対象外とするもの

- 異常系 E2E
- retry 付きの flaky 吸収ロジック
- 画面ピクセル一致や screenshot 比較ベースの厳密検証
- 1 本の巨大シナリオでの全コマンド直列実行

## 9. 実装順の推奨

1. S01 で server / attach / snapshot の共通基盤を固める
2. S03, S04, S06 のような比較的安定な操作系を先に通す
3. S07, S05 のような待機・低レベル入力系を後から追加する
4. S08, S09, S10 の lifecycle / file 系で全登録コマンドを閉じる

この順序により、基盤不備と個別コマンド不備を切り分けやすくする。
