# 問題点調査結果

## 調査概要

- 対象: `src/` と `tests/`
- 除外: `docs/` 配下の内容と品質評価、`discussion/` 配下の過去メモの品質評価、実装修正そのもの、実測・再現手順の深掘りを伴う詳細検証
- 観点: `discussion/035_問題点調査観点.md` で定義した仕様・使いやすさ、設計、実装・不具合、非機能、テスタビリティ、テスト実装の観点

本メモは、ADACT の問題点や改善余地をフラットに洗い出すため、`src/` / `tests/` の調査結果を整理したもの。各指摘は可能な範囲で「事実」と「解釈」を分け、後続で優先順位付けや修正方針検討をしやすい粒度に留める。

---

## 全体結論

- 致命的な設計崩壊は見当たらない。
- 一方で、daemon の長時間稼働、セッション / プロセス lifecycle、AI 向け UX、テスト安定性には改善余地が複数ある。
- 特に、所有権が曖昧な resource lifecycle、異常系での診断しやすさ、ポーリングや retired ref による長時間稼働時の非機能リスクは早めに整理する価値がある。
- このうち、今回の 5 件の対応テーマ（`SessionStore` / `UiaEngine` 所有権整理、`CloseAllAsync`、`windows_screenshot`、`KillAsync`、および HTTP E2E 起動失敗の明確化を含む実アプリテスト改善）は実装・独立検証・レビュー完了済み。

## 優先度高の指摘

### 1. `SessionStore` が DI 管理の `UiaEngine` を dispose しており、所有権が曖昧

- 分類: 設計
- 対象: `src/Adact.Mcp.Common/SessionStore.cs`
- 優先度: 高
- 修正難易度: 中
- 対応状況: 対応済み

#### 対応前の事実（調査時点）

- `SessionStore` はコンストラクタで `UiaEngine` を受け取り、`Engine` プロパティとして公開している（`SessionStore.cs:35-44`）。
- `SessionStore.Dispose()` は保持中の session に加えて `_engine.Dispose()` を呼び出している（`SessionStore.cs:130-146`）。

#### 解釈

- DI 管理オブジェクトを利用側が dispose する構造は、将来的な lifetime 変更や複数利用時に破綻しやすい。
- HTTP host では `UiaEngine` と `SessionStore` がどちらも Singleton DI 登録されており、DI コンテナ管理の lifetime と `SessionStore` 内部の所有権境界が読み取りづらい。
- daemon の長時間稼働や複数 session 操作において、意図しない premature dispose / 二重 dispose / 後続操作失敗の温床になり得る。
- 改善方向としては、`UiaEngine` の所有者を DI 側に寄せるか、`SessionStore` が所有する resource を明確に分離するのが望ましい。

#### 対応結果

- `SessionStore` は `UiaEngine` を所有しない形に整理された。
- `SessionStore.Dispose()` から `UiaEngine.Dispose()` 呼び出しは除去され、所有権は DI / 上位管理側に寄せられた。

### 2. HTTP E2E の電卓起動失敗時に明確な例外にならない

- 分類: テスト実装 / 実装・不具合
- 対象: `tests/Adact.Mcp.Http.Tests/E2E/CalculatorHttpE2ETests.cs`
- 優先度: 高
- 修正難易度: 低
- 対応状況: 対応済み

#### 対応前の事実（調査時点）

- `CalculatorHttpE2ETests.AttachAndSnapshot_OnCalculator_ReturnsTreeWithButtons()` は電卓アプリの起動を前提に `windows_list_apps` / `windows_attach` / `windows_snapshot` を検証している（`CalculatorHttpE2ETests.cs:50-113`）。
- ローカル server 利用時の `StartCalculator()` は `calc.exe` を起動し、10 秒以内に `CalculatorApp` process が見つからなくても例外を投げず、`Process?` を返している（`CalculatorHttpE2ETests.cs:133-147`）。

#### 解釈

- E2E の前提条件失敗が不明瞭だと、実装不具合と環境依存の切り分けが難しくなる。
- 起動に失敗した場合、失敗原因が「電卓起動失敗」として明確に表現されず、後続の操作失敗として見える可能性がある。
- ローカル実行や CI 調査時の診断コストを増やし、flaky test の原因分析を妨げる。
- 改善方向としては、起動直後に process / window 取得結果を検証し、失敗時は前提条件エラーとして明確なメッセージを出すのがよい。

#### 対応結果

- `CalculatorHttpE2ETests` などの実アプリ起動失敗は、後続操作失敗ではなく前提条件エラーとして明示されるよう整理された。
- あわせて、固定 sleep の一部を条件待ちへ置換し、実アプリ E2E / smoke 系テストの安定化を進めた。

## 優先度中の主要指摘

### 1. `CloseAllAsync` のコメントが示す継続範囲に対して例外処理範囲が限定的

- 分類: 実装・不具合 / 保守性
- 対象: `src/Adact.Mcp.Common/WindowsTools.cs`
- 優先度: 中
- 修正難易度: 低
- 対応状況: 対応済み

#### 対応前の事実（調査時点）

- `WindowsTools.CloseAllAsync()` の XML コメントは、現在 attach 中の全 session に対して close を試行し、session 単位の結果配列を返すと説明している。特に remarks は「individual close failures do not prevent attempts for remaining sessions」と読める（`WindowsTools.cs:522-530`, method: `CloseAllAsync`）。
- `CloseAllAsync()` の実装は `_store.ListAll()` の snapshot を走査し、`session.CloseAsync()` 成功時は `_store.TryRemove()` と `DetachSession()` を呼び出す一方、継続して `fail` を記録する catch 対象は `CloseFailedException` のみである（`WindowsTools.cs:555-565`, method: `CloseAllAsync`, catch: `CloseFailedException`）。

#### 解釈

- コメントからは全 session への close 試行継続を広く期待しやすいが、実装で継続扱いになる例外は `CloseFailedException` に限定されている。
- この差異は、利用側や後続実装者に close / detach / ref 整理と例外伝播の責務境界を誤って理解させる可能性がある。
- コメントまたは実装意図を合わせる必要がある。
- 改善方向は、コメントを実装に合わせるか、コメントに合わせて実装意図を明確化する程度の局所対応でよい。

#### 対応結果

- `OperationCanceledException` 以外は session 単位の失敗結果に落として継続する実装へ整理された。
- 失敗有無を呼び出し側が判断できるよう `hasFailures` が返されるようになり、コメントが期待する継続挙動に近づいた。

### 2. `KillAsync` の PID 再利用リスク

- 分類: 実装・不具合
- 対象: `src/Adact.Engine/WindowSession.cs`
- 優先度: 中
- 修正難易度: 低
- 対応状況: 対応済み

#### 対応前の事実（調査時点）

- `WindowSession.KillAsync()` は session に保持した `_processId` を使い、`Process.GetProcessById(_processId)` で取得した process に対して `p.Kill(entireProcessTree: true)` を呼び出す。直前コメントにも PID 再利用対策が TODO として残っている（`WindowSession.cs:380-391`, method: `KillAsync`）。

#### 解釈

- 元のプロセス終了後に OS が PID を再利用した場合、理論上は別プロセスを対象にするリスクがある。
- 発生頻度は高くないと考えられるが、プロセス終了操作は影響が大きいため、process start time などで同一性を確認できると安全性が上がる。

#### 対応結果

- `WindowInfo` に `ProcessStartTimeUtc` が保持され、`KillAsync` で PID に加えて start time の同一性確認が入った。
- start time の取得不能時や不一致時は安全側で kill を拒否する挙動となった。

### 3. `windows_screenshot` の `ref` + `sessionId` 同時指定時に `sessionId` が黙って無視される

- 分類: 仕様・使いやすさ / 実装・不具合
- 対象: `src/Adact.Mcp.Common/WindowsTools.Screenshot.cs`
- 優先度: 中
- 修正難易度: 低
- 対応状況: 対応済み

#### 対応前の事実（調査時点）

- `WindowsTools.ScreenshotAsync()` は `ref` 指定時に `ValidateRef` path へ入り、`sessionId` path は `else` 側でのみ実行される。最終的な `ScreenshotAsync` 呼び出しにも `ref` の有無で ref / null を渡しているため、`ref` と `sessionId` を同時指定した場合は `ref` 側が優先され、`sessionId` は明示的なエラーにならない（`WindowsTools.Screenshot.cs:43-59`, method: `ScreenshotAsync`, branch: `if (!string.IsNullOrWhiteSpace(refId)) ... else ...`）。

#### 解釈

- AI / 人間利用者のどちらにとっても、矛盾する指定が黙って処理されると誤操作に気づきにくい。
- 改善方向としては、同時指定を validation error にするか、仕様として明確に文書化した上でレスポンスに警告を含めることが考えられる。

#### 対応結果

- `ref` と `sessionId` の同時指定は `INVALID_ARGUMENT` を返すようになった。
- screenshot 専用の引数解決経路が設けられ、関連する引数解決エラーも `INVALID_ARGUMENT` に統一された。

### 4. `WindowRefStore` が retired entry を永久保持するメモリ増加懸念

- 分類: 非機能
- 対象: `src/Adact.Mcp.Common/WindowRefStore.cs`
- 優先度: 中
- 修正難易度: 低
- 対応状況: 対応済み
- 対応結果: session close/detach 掃除 + TTL purge 追加

#### 事実

- `WindowRefStore` は retired 状態の ref entry を保持する設計になっている。
- `WindowRefStore` は `Dictionary<WindowKey, WindowRefEntry>` に entry を保持し、`RetireMissing()` では entry の `Retired` を `true` に更新している（`WindowRefStore.cs:16-17`, `:59-88`）。

#### 解釈

- 短時間利用では問題化しにくいが、daemon 常駐や大量操作ではメモリ増加要因になり得る。
- 明確な pruning / 上限管理がない場合、daemon 長時間稼働で retired entry が蓄積し続ける可能性がある。
- 改善方向としては、TTL、最大件数、session close 時の削除など、用途に合う整理戦略を検討するのがよい。

### 5. `wait_for` 系がポーリングごとにフル snapshot を再構築する性能懸念

- 分類: 非機能
- 対象: `src/Adact.Engine/WindowSession.Wait.cs`, `src/Adact.Engine/SnapshotBuilder.cs`
- 優先度: 中
- 修正難易度: 中
- 対応状況: 対応済み
- 対応結果: 軽量探索 path 追加

#### 事実

- `WindowSession.Wait` の `TakeInternalSnapshot` は poll ごとに呼ばれる snapshot 取得処理で、対象 window の取得後に `new SnapshotBuilder(_registry).Build(input)` を実行している（`WindowSession.Wait.cs:205-232`, local function: `TakeInternalSnapshot`, symbol: `SnapshotBuilder.Build`）。

#### 解釈

- UI tree が大きいアプリや待機時間が長いケースでは、CPU / UIA 呼び出し回数が増え、レスポンス悪化につながる可能性がある。
- 改善方向としては、対象 ref / 条件に応じた限定探索、ポーリング間隔調整、軽量 query path の導入などが候補になる。

### 6. daemon 自動起動後の再接続 retry が薄い

- 分類: 仕様・使いやすさ / 実装・不具合
- 対象: `src/Adact.Cli.Core/Commands/CommandHelpers.cs`
- 優先度: 中
- 修正難易度: 低
- 対応状況: 対応済み
- 対応結果: bounded reconnect retry 追加

#### 事実

- `CommandHelpers.RunWithClientAndAutoStartAsync()` は、Named Pipe server 未起動時に `TryAutoStartServerAsync` を実行し、成功後に `ConnectNamedPipeClientAsync` を 1 回呼び出している（`CommandHelpers.cs:179-194`）。

#### 解釈

- daemon 起動直後は listen 開始までに時間差があり、環境によっては初回接続が失敗しやすい。
- 自動起動成功後の再接続 retry は限定的と解釈できる。
- AI からの連続操作では「たまたま失敗」に見えるため、短時間 retry やエラーメッセージ改善の効果が大きい。

### 7. Named Pipe と HTTP で session 共有セマンティクスが異なる可能性

- 分類: 設計 / 仕様・使いやすさ
- 対象: `src/Adact.Cli.Server/NamedPipe/NamedPipeConnection.cs`, `src/Adact.Cli.Server/HttpHost.cs`
- 優先度: 中
- 修正難易度: 中
- 対応状況: 対応済み
- 対応結果: Named Pipe 共有状態化。接続跨ぎ list-apps → attach 検証済み

#### 事実

- Named Pipe では `NamedPipeConnection.RunAsync()` が接続ごとに `ServiceCollection` / `ServiceProvider` を構築し、`UiaEngine` / `SessionStore` / `WindowRefStore` を登録している（`NamedPipeConnection.cs:54-80`）。
- HTTP では `HttpHost.BuildApplication()` が application builder の service collection に `UiaEngine` / `SessionStore` / `WindowRefStore` を Singleton 登録している（`HttpHost.cs:92-132`）。

#### 解釈

- 差異が意図的であれば問題ないが、利用者視点では transport を変えたときの session 共有挙動が分かりづらくなる可能性がある。
- 上記により、Named Pipe 経由と HTTP 経由で session / connection の扱いが異なる構造と解釈できる。
- 改善方向としては、意図したセマンティクスを明文化し、必要なら実装とテストで transport 間の差異を固定するのがよい。

### 8. `CommandHelpers` の static 差し替えがテスト並列性を制約

- 分類: テスタビリティ / テスト実装
- 対象: `src/Adact.Cli.Core/Commands/CommandHelpers.cs`
- 優先度: 中
- 修正難易度: 中
- 対応状況: 対応済み
- 対応結果: `CommandRuntime` 注入

#### 事実

- `CommandHelpers` は `ConnectHttpClientAsync` / `ConnectNamedPipeClientAsync` / `IsServerRunningAsync` / `TryAutoStartServerAsync` を static delegate として持ち、テストで依存を切り替えられる構造になっている（`CommandHelpers.cs:17-34`, symbols: static delegate fields）。

#### 解釈

- static mutable state はテスト間干渉を生みやすく、並列実行を制約する。
- 現状のテスト制御で成立していても、テスト追加やアセンブリ分割に伴い flaky になる可能性がある。
- 改善方向としては、依存注入可能な context / service に寄せるか、差し替え範囲をテストごとに閉じ込める設計を検討する。

### 9. 電卓起動待ちが固定 sleep で flaky になり得る

- 分類: テスト実装
- 対象: `CalculatorSmokeTests`, `CalculatorSnapshotTests`, `CalculatorCliE2ETests`, `CalculatorHttpE2ETests`
- 優先度: 中
- 修正難易度: 低
- 対応状況: 対応済み（今回対象の 4 テスト群）

#### 対応前の事実（調査時点）

- `CalculatorSmokeTests` では電卓起動後の待機に固定 sleep を使っていた（`tests/Adact.Engine.Tests/Smoke/CalculatorSmokeTests.cs` の調査時点実装）。
- `CalculatorSnapshotTests` では電卓起動後の待機に固定 sleep を使っていた（`tests/Adact.Engine.Tests/IntegrationUia/CalculatorSnapshotTests.cs` の調査時点実装）。
- CLI / HTTP の Calculator E2E tests でも電卓起動後の待機に固定 sleep を使っていた（`tests/Adact.Cli.Tests/E2E/CalculatorCliE2ETests.cs`, `tests/Adact.Mcp.Http.Tests/E2E/CalculatorHttpE2ETests.cs` の調査時点実装）。

#### 解釈

- 固定 sleep は遅い環境では不足し、速い環境では不要な待ちになる。
- 改善方向としては、window 出現や UI 要素取得を条件にした待機へ置き換えるのがよい。

#### 対応結果

- 今回対象にした `CalculatorSmokeTests` / `CalculatorSnapshotTests` / `CalculatorCliE2ETests` / `CalculatorHttpE2ETests` の 4 テスト群では、電卓起動待ちが `CalculatorTestHelper` による条件待ちへ置換された。
- CLI / HTTP / Engine の関連する実アプリテストは通過しており、今回対象範囲では固定 sleep 起因の不安定さの低減を確認できた。
- この節の元の指摘内容は調査時点の問題メモとして残しつつ、上記 4 テスト群については現行実装では解消済みである。

### 10. 環境変数を書き換えるテストがアセンブリ間並列で干渉し得る

- 分類: テスト実装 / テスタビリティ
- 対象: CLI / HTTP tests
- 優先度: 中
- 修正難易度: 低
- 対応状況: 対応済み
- 対応結果: 注入化

#### 事実

- HTTP 側の `AdactHttpServerFixtureTests` と CLI 側の `AdactDaemonFixtureTests` には `EnvironmentVariableScope` があり、`ADACT_SERVER_URL` を退避・変更・復元して fixture の挙動を検証している（`AdactHttpServerFixtureTests.cs:58-73`, `AdactDaemonFixtureTests.cs:56-72`, tests: fixture environment variable tests）。

#### 解釈

- 環境変数は process global な状態であり、アセンブリ間や並列実行時に干渉し得る。
- 改善方向としては、テスト collection の直列化、環境変数の退避・復元徹底、または process 分離を検討するのがよい。

## 残件レビュー時の指摘

残件 6 件の実装レビューにおいて、実装自体はすべて正と判定されたが、以下の Low 指摘 4 件が併せて挙げられた。

### 1. `OperationCanceledException` が `catch (Exception ex)` で捕捉される

- 箇所: `CommandHelpers.cs:157-159, 174-176`
- 分類: 実装・不具合
- 優先度: Low
- 内容: Ctrl+C 等のキャンセル操作による `OperationCanceledException` が汎用例外ハンドラで捕捉されるため、キャンセルが伝播せず誤ったエラーメッセージ（「サーバー未起動」等）になる可能性がある。

### 2. `throw last ?? new TimeoutException(...)` が到達不能コード

- 箇所: `CommandHelpers.cs:211`
- 分類: 実装・不具合
- 優先度: Low
- 内容: ループ内で必ず脱出する構造のため、この throw 文には実際には到達しない。

### 3. 自動起動後 retry 切れ時のエラーメッセージが誤解を招く

- 箇所: `CommandHelpers.cs:112-119`
- 分類: 仕様・使いやすさ
- 優先度: Low
- 内容: retry 上限到達時に "No ADACT server is running." と出力されるが、実際には自動起動に成功した後の再接続失敗であり、エラーメッセージが実態と合っていない。

### 4. `DaemonSpawner` が静的ミュータブルプロパティのまま

- 箇所: `DaemonSpawner.cs:20, 27`
- 分類: テスタビリティ
- 優先度: Low
- 内容: `CommandHelpers` は `CommandRuntime` による注入化が完了しているが、`DaemonSpawner` の依存は未移行で静的ミュータブルプロパティのまま残っている。
