# 027 操作ブロック検知 — ロック / UAC / その他による操作失敗の原因切り分け

> 関連: [018 対話セッション判定](018_対話セッション判定.md) / [019 Phase8以降の残タスク整理](019_Phase8以降の残タスク整理.md)
> 作成日: 2026-05-01 (JST)

---

## 1. 背景

### 1.1 既存の対話セッション判定との違い

[018 対話セッション判定](018_対話セッション判定.md) は **daemon 起動時** に「UIA が使えるセッションか」を判定する。対象は `serve` / `local` の起動ガードであり、SSH / サービス経由の Session 0 起動を防ぐ。

一方、本機能は **操作実行時** に「操作が実際に届くデスクトップ状態か」を判定する。対象は `Win + L` による画面ロック、UAC プロンプト中、別ユーザーの切り替えなど、**対話セッション内でも操作が遮断されるケース**である。

| 状態 | 対話セッション判定 (起動時) | 操作ブロック検知 (実行時) |
| --- | --- | --- |
| 通常のデスクトップ | ✅ OK | ✅ 操作可能 |
| SSH / サービス起動 (Session 0) | ❌ NG (`NO_INTERACTIVE_SESSION`) | — |
| **Win + L 画面ロック** | ✅ OK (WinSta0 所属) | ❌ **操作ブロック** |
| **UAC プロンプト中** | ✅ OK (WinSta0 所属) | ❌ **操作ブロック** |
| **別ユーザーに切り替え** | ✅ OK (WinSta0 所属) | ❌ **操作ブロック** |

### 1.2 問題の本質

UIA は画面ロック中でも「ウィンドウが見える」状態（tree 取得は可能）だが、実際の click / key input は届かない。このため:

- `list-apps` は正常にリストを返す
- `snapshot` は取得できる
- `click` / `fill` / `press` などが不可解に失敗する
- 利用者は「ウィンドウはあるのに操作が失敗する」と判断しづらい

本機能はこの **原因切り分け** を自動化する。

---

## 2. 目的

操作（click / fill / snapshot / wait など）が失敗した際、**デスクトップ状態が操作を遮断しているかをベストエフォートで診断**し、明確なエラーコードで返す。

これにより:

- 利用者は「操作失敗の原因がアプリ側か環境側か」を即座に判断できる
- AI クライアントは `OPERATION_BLOCKED` を受信した際に「ロック解除を促す」などの復旧アクションを提示できる

---

## 3. スコープ

### 3.1 対象

- **診断タイミング**: 操作が失敗した**直後**（catch ブロック内でベストエフォート診断）
- **対象操作**: 全操作（`SnapshotAsync`, `ClickAsync`, `FillAsync`, `PressAsync`, `TypeAsync`, `HoverAsync`, `MouseMoveAsync`, `MouseDownAsync`, `MouseUpAsync`, `MouseWheelAsync`, `CheckAsync`, `UncheckAsync`, `SelectAsync`, `FocusAsync`, `ClearAsync`, `ScrollIntoViewAsync`, `ResizeAsync`, `MinimizeAsync`, `MaximizeAsync`, `RestoreAsync`, `CloseAsync`, `KillAsync`, `WaitForRefAsync`, `WaitForQueryAsync`, `InspectAsync`, `ScreenshotAsync` など）
- **診断内容**: 以下 3 項目のいずれかに該当する場合 `OPERATION_BLOCKED` とする
  1. セッションがロック状態（`WTSQuerySessionInformation` + `WTS_SESSIONSTATE_LOCK`）
  2. 入力デスクトップが通常ではない（`OpenInputDesktop` + 名前判定）
  3. 対象ウィンドウが非アクティブ / 不可視（`IsWindowVisible` / `GetForegroundWindow`）

### 3.2 非対象

- daemon 起動時のセッション判定（018 の責務）
- 操作が成功するケースでの事前チェック（オーバーヘッド削減のため）
- 操作失敗の原因が「操作ブロック」以外の場合（従来通りの例外を返す）

---

## 4. 要件

### 4.1 機能要件

- F1. 操作が失敗した際、**ベストエフォート**でデスクトップ状態を診断する
- F2. 診断は **3 つの独立した観点**（セッションロック / 入力デスクトップ / ウィンドウ状態）から行い、**いずれかに該当すればブロック判定**とする
- F3. ブロック判定時は `OperationBlockedException` を throw し、原因の詳細をメッセージに含める
- F4. 診断 API 呼び出しが失敗しても、**元の例外は失われない**（診断失敗時は元の例外をそのまま throw）
- F5. 診断は **同期 API 呼び出し**で行い、タイムアウトや重い処理は避ける（数 ms で完了）

### 4.2 非機能要件

- N1. 診断は操作失敗時のみ行うため、通常時のオーバーヘッドはゼロ
- N2. 追加依存は P/Invoke のみ。新規 NuGet 参照は増やさない
- N3. 診断ロジックは純関数化し、Unit テスト（L1）でカバーする
- N4. 既存の `--server` 接続経路や `daemon-stop` の動作には影響を与えない

## 5. 設計

### 5.1 診断ロジック

#### 入力

- `sessionId`: `Process.GetCurrentProcess().SessionId`
- `windowHwnd`: 操作対象ウィンドウの HWND

#### 判定ルール

```
IsSessionLocked(sessionId)      → true  → blocked (reason: locked)
IsSecureDesktopActive()         → true  → blocked (reason: secure desktop)
IsWindowBlocked(windowHwnd)     → true  → blocked (reason: window not visible or not foreground)
上記いずれにも該当しない            → not blocked
```

#### 各診断の詳細

| 診断 | API | 判定条件 |
| --- | --- | --- |
| セッションロック | `WTSQuerySessionInformation(WTS_CURRENT_SERVER_HANDLE, sessionId, WTS_SESSIONSTATE_LOCK, ...)` | 戻り値が `WTS_SESSIONSTATE_LOCK` 相当の locked 状態 |
| セキュアデスクトップ | `OpenInputDesktop(0, false, DESKTOP_READOBJECTS)` → `GetUserObjectInformation(UOI_NAME)` | 名前が `"Default"` 以外 |
| ウィンドウ非アクティブ | `IsWindowVisible(hwnd)` + `GetForegroundWindow()` | `false` または foreground ではない |

補足:

- `WTSQuerySessionInformation` は Terminal Services API であり、リモートデスクトップセッションの状態も問い合わせ可能
- `OpenInputDesktop` は「現在入力を受け付けているデスクトップ」を返す。UAC プロンプト中は `"Winlogon"` セキュアデスクトップになる
- ウィンドウ状態は既存 `NativeMethods.IsWindowVisible` を再利用

### 5.2 配置

| 要素 | 配置 | 備考 |
| --- | --- | --- |
| WTS API P/Invoke | `Adact.Engine/NativeMethods.cs` | `WTSQuerySessionInformation`, `WTSFreeMemory`, `OpenInputDesktop`, `CloseDesktop`, `GetForegroundWindow` を追加 |
| 診断クラス | `Adact.Engine/OperationBlockerDetector.cs` (新規) | `static OperationBlockerResult Detect(int sessionId, nint windowHwnd)` という純関数 |
| 診断結果型 | `Adact.Engine/OperationBlockerResult.cs` (新規) | `readonly record struct OperationBlockerResult(bool IsBlocked, string? Reason)` |
| 例外クラス | `Adact.Engine/Exceptions/OperationBlockedException.cs` (新規) | `AdactException` を継承 |
| 呼び出し点 | `Adact.Engine/WindowSession.cs` | `RunSerializedAsync` の catch ブロック内で `Detect` を呼び出し、blocked なら `OperationBlockedException` に置き換え |
| エラーコード | `Adact.Cli/Output/ErrorCodes.cs` / `Adact.Mcp.Common/ToolErrors.cs` | `OPERATION_BLOCKED` を追加 |

### 5.3 例外変換フロー

```
WindowSession.RunSerializedAsync
  try {
    action()  // 操作実行
  }
  catch (Exception ex) {
    // 1. 既に AdactException はそのまま再throw
    if (ex is AdactException) throw;

    // 2. 診断実行
    var blocked = OperationBlockerDetector.Detect(currentSessionId, windowHwnd);

    // 3. ブロック判定時は OperationBlockedException に置き換え
    if (blocked.IsBlocked) {
      throw new OperationBlockedException(blocked.Reason!, ex);
    }

    // 4. ブロックでなければ元の例外をそのまま
    throw;
  }
```

注意:

- `OperationBlockedException` の内部例外（`InnerException`）には元の例外を保持する
- 診断 API が失敗した場合は「元の例外をそのまま throw」でフォールバックする
- `AdactException` のサブクラス（`RefNotFoundException`, `ElementInteractionException` など）は既に階層化されているため、それらは診断対象外とする

### 5.4 終了コード / エラー出力

`Adact.Cli/Output/ErrorCodes.cs` / `Adact.Mcp.Common/ToolErrors.cs` に追加:

| 名前 | 値 (string) |


`OperationBlockerDetector` の純関数部分を mocking してテスト。

- `Detect(sessionId=0, windowHwnd=0)` → `IsBlocked=true` (session 0 は通常ロック)

### 6.2 L2 Integration (`Adact.Engine.Tests`)

`WindowSession` の fake element ベーステストで、操作が失敗し、かつ「ブロック状態」シミュレート時に `OperationBlockedException` が出ることを確認。

- `ClickAsync` が失敗 → `OperationBlockedException` に置き換えられる
- `FillAsync` が失敗 → `OperationBlockedException` に置き換えられる
- ブロック状態でない場合 → 元の `ElementInteractionException` がそのまま

### 6.3 手動スモーク

実装後に開発者が一度確認する手順:

1. **正常系（ロックなし）**
   ```powershell
   adact serve
   adact attach <wref>
   adact click s1e1
   # 正常にクリックされる
   ```

2. **異常系（Win + L ロック）**
   ```powershell
   # 対話セッションで adact serve を起動した状態で
   Win + L で画面ロック
   # 別の対話セッションから（または事前に接続済みの CLI から）
   adact click s1e1
   # exit code 1、stderr に OPERATION_BLOCKED (desktop session is locked)
   ```

3. **異常系（UAC プロンプト）**
   ```powershell
   # 管理者権限を要求するアプリを起動して UAC プロンプトを出した状態で
   adact click s1e1
   # exit code 1、stderr に OPERATION_BLOCKED (secure desktop is active)
   ```

## 7. 既知の制約 / 後続課題

- C1. 診断は「ベストエフォート」であり、100% 網羅ではない。例: 一部の UAC 設定（"Never notify"）ではセキュアデスクトップが使われないため検知できない
- C2. 診断は **操作失敗後** に行うため、ロック中に `snapshot` が成功するケース（UIA tree は取得できる）では `OPERATION_BLOCKED` は出ない。これは仕様通り（snapshot 自体は成功しているため）
- C3. 将来、操作実行**前**の事前チェックを追加したい場合は別途検討（毎回の API コールによるオーバーヘッドとトレードオフ）
- C4. Terminal Services API (`wtsapi32.dll`) は Windows Server で利用可能だが、一部の制限付き環境では動作しない可能性がある。P/Invoke 失敗時はフォールバック（元の例外維持）で対応

### 9.4 設計からの差分

| 設計記述 | 実装結果 | 理由 |
| --- | --- | --- |
| `WTSQuerySessionInformation` の `pBytesReturned` は `int` | `uint` に変更 | API 定義との整合性 |
| ウィンドウ非アクティブ検知は `IsWindowVisible` + `GetForegroundWindow` のみ | フォアグラウンドウィンドウのプロセス名確認（`LockApp` / `LogonUI`）を追加 | RDP / VS Code Server 環境で `OpenInputDesktop` が常に `"Default"` を返す問題への対処 |
| `catch (AdactException)` で早期 return | `catch (OperationBlockedException)` に変更 | `ElementInteractionException` 等の `AdactException` サブクラスも Detect の対象にするため |

### 9.5 既知の制約

- リモートデスクトップ / VS Code Server 環境では、物理ディスプレイ側のロック状態とセッション状態が異なる場合がある
- フォアグラウンドウィンドウのプロセス名確認（`LockApp` / `LogonUI`）は、ロック画面以外のケースでは誤検知しないよう設計されたが、将来的に他のプロセス名も追加する可能性がある
