## いつ使うか

- あらゆる実装タスクを実行するとき（コード・docs・設定のいずれも対象）
- 実装担当エージェントを起動する前
- コード・ドキュメント・設定を変更する前

typo 修正や軽微な変更であってもレビューは必ず実施する。

## 基本方針

- **司令塔 Codex が実装担当とレビュー担当を交互に呼ぶ**
- 実装担当は自分でレビュー担当を呼ばない。レビューの制御は司令塔が一元管理する
- レビュー担当は、司令塔から指定された範囲を調査・テスト実行・報告する
- **指摘ゼロになるまで**ループを繰り返す
- **10 回で強制停止** し、ユーザに判断を仰ぐ

## 基本フロー

```
司令塔 Codex
  ├─ (1) 軽微なら直接実装 / 通常は実装担当を起動 → 実装
  ├─ (2) 司令塔が差分と診断コマンドで独立検証 (必須)
  ├─ (3) レビュー担当を起動 → レビュー
  ├─ (4) 指摘あり: 軽微なら直接修正 / 通常は実装担当に修正依頼 → (2) に戻る
  └─ (5) 指摘なし: 完了
```

1. 司令塔がタスク内容と設計を確認する
2. 軽微な変更は司令塔が直接実装してよい。通常の実装は実装担当エージェントに依頼する
3. **実装完了直後、司令塔は差分確認と診断コマンドによる独立検証を必ず行う**。実装担当自身の自己報告 (ビルド OK / フォーマット済み等) は信用しすぎず、`git diff`、該当する `dotnet build` / `dotnet test` / `dotnet format --verify-no-changes` などで再検証する。問題があればレビュー担当を起動する前に、軽微な変更は司令塔が直接修正し、通常の変更は実装担当を再起動して修正する。
4. 司令塔がレビュー担当エージェントにレビューを依頼する
5. レビュー担当の報告を受け、指摘があれば軽微な変更は司令塔が直接修正し、通常の変更は実装担当に修正を依頼する (修正後も再度、差分確認と診断コマンドを走らせる)
6. 指摘がゼロになるまで 4〜5 を繰り返す
7. 10 回に達したら強制停止し、ユーザに報告する

### 独立検証を必ず行う理由

実装担当は `dotnet format` / `dotnet build` / `dotnet test` を実行したと報告しても、実際には実行に失敗している / 一部プロジェクトだけを対象にしている / 変更後の差分が想定とずれている、といった齟齬が発生し得る。司令塔はレビュー担当に渡す前に、変更差分と該当コマンドを自分で確認し、明らかなビルド・テスト・フォーマット違反を早期に潰す。

## ループ停止条件

| 条件                       | 動作                   |
| -------------------------- | ---------------------- |
| レビュー担当の指摘がゼロ  | 正常終了               |
| ループ回数が 10 回に達した | 強制停止、ユーザに報告 |

## レビュー観点の指定

**司令塔がタスク内容に応じて動的に指定**する。以下の観点例集から選択・組み合わせてレビュー担当に渡す。

### 共通観点

- 要件を満たしているか
- 副作用・リグレッションがないか
- 既存コード／docs との一貫性
- リンク切れ・参照切れがないか
- 該当する診断コマンドで warning/error が残っていないか
- 該当するビルドコマンドで warning/error が 0 であるか

### コード実装タスク

- ロジックの正しさ
- エラーハンドリング
- テストの有無・妥当性
- コード規約準拠
- セキュリティ上の問題

### docs 更新タスク

- コードとの整合性（記述と実装の一致）
- リンク切れ
- 用語統一との整合
- 既存 docs スタイル準拠
- TODO マーカーの適切な使用

### 設定変更タスク

- 既存機能への影響
- 依存コンポーネントへの波及

## 実装担当エージェント起動プロンプト

司令塔が実装担当を呼ぶときは、以下の要素を必ず含める。

- **タスク内容**: 何を実装するか
- **参照すべき設計ドキュメント**: `discussion/` 配下のファイルなど
- **参照すべき docs**: 関連する `docs/` を明示
- **成果物の明示**: 作成・変更するファイルのパス
- **制御に関する指示**:
  - 「完了したら速やかに司令塔に制御を戻すこと」
  - **「レビュー担当は呼ばない。レビューは司令塔が担当する」** を必ず明記

### テンプレート例

```
タスク: <実装内容>
設計: <discussion/XXX.md 等>
参照 docs: <docs/api/xxx.md 等>
成果物: <ファイルパス一覧>

注意:
- レビュー担当エージェントは呼ばないでください。レビューは司令塔が担当します。
- 実装が完了したら速やかに司令塔に制御を戻してください。
```

## レビュー担当エージェント起動プロンプト

司令塔がレビュー担当を呼ぶときは、以下の要素を必ず含める。

- **レビュー対象ファイル一覧**: 絶対パスまたは workspace 相対パス
- **レビュー観点**: 上記観点例集からタスクに応じて選択
- **実行すべきテスト**: 該当するビルド・テスト・静的解析コマンド。指定が難しい場合は、変更範囲に見合う最小限のテスト選定を依頼する
- **「コード修正は不要、テスト実行・調査・報告のみ」** を必ず明記
- **「指摘がゼロの場合はその旨を明記」** を必ず明記
- 「完了したら速やかに司令塔に制御を戻すこと」
- **報告フォーマット**: 指摘箇所 / 指摘内容 / 修正提案

### テンプレート例

```
レビュー対象:
- <ファイルパス 1>
- <ファイルパス 2>

観点:
- <観点 1>
- <観点 2>

実行すべきテスト:
- <テストコマンドまたはテスト選定方針>

注意:
- コード修正は不要です。テスト実行、調査、報告のみ行ってください。
- 指摘がゼロの場合は「指摘なし」と明記してください。
- 完了したら速やかに司令塔に制御を戻してください。

報告フォーマット:
- 指摘箇所（ファイル:行）
- 指摘内容
- 修正提案
```

## 10 回到達時の報告フォーマット

ループが 10 回に達したら、司令塔はユーザに次の形式で報告する。

```
レビューループが 10 回に達しました。以下の状況です:

## 現在の指摘事項
- 項目 1: ...
- 項目 2: ...

## これまでの修正履歴
- 1 回目: ...
- 2 回目: ...
...

## 判断をお願いします
- このまま続行（11 回目以降も回す）
- 別方針に切り替え
- 現状で一旦中断してユーザ側で手動対応
```

## docs 更新との連携

実装完了後の docs 更新も本ループに組み込む。コード・仕様・操作・設定・テスト方針に影響する変更では、関連 docs 更新を完了条件に含める。

1. 実装タスク（コード変更）を本ループで完了させる
2. 関連 docs を特定し、**docs 更新そのものを実装タスクとして扱い、本ループを再適用する**
3. 実装担当が docs を更新 → レビュー担当が「コード整合・リンク・用語統一」観点でレビュー → 指摘ゼロまで繰り返す

これによりコード・docs ともに同じ品質保証プロセスを通る。

## 動作例（REST API 追加タスク）

```
1. 司令塔: タスク理解・設計確認
2. 司令塔 → 実装担当:
   「/api/xxx を実装してください。設計は discussion/XXX.md 参照。
    docs/api/rest.md も参照してください。完了したら司令塔に戻してください。
    レビュー担当は呼ばないでください。」
3. 司令塔 → レビュー担当:
   「web/backend/src/api/xxx.ts をレビューしてください。
    観点: 仕様整合、エラーハンドリング、既存 API との一貫性、ErrorCode の適切性。
    コード修正は不要、テスト実行・調査・報告のみ。指摘ゼロなら明記してください。」
4. レビュー担当: 「エラーハンドリング未実装箇所 1 件」
5. 司令塔 → 実装担当: 「レビュー指摘を修正してください: ...」
6. 司令塔 → レビュー担当: 「再レビューしてください」
7. レビュー担当: 「指摘なし」
8. 司令塔 → 実装担当: 「docs/api/rest.md を更新してください」
9. 司令塔 → レビュー担当: 「docs をレビューしてください。
    観点: コード整合、リンク、用語統一」
10. レビュー担当: 「指摘なし」
11. 完了報告
```
